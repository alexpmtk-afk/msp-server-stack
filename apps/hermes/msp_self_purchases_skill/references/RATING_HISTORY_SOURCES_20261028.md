# История оценок: источник и дата собственного отзыва

Канон в репозитории: `docs/self-purchases/RATING_HISTORY_SOURCES_20261028.md`.
Дата события — только «Дата отзыва» / review_date, не дата покупки.
Владелец указывает собственную оценку 5★; тексты не требуются.

Показывать отдельно рейтинг карточки накануне события/на последнюю
доступную дату и распределение полученных отдельных оценок по 1–5★.
Пустой текст не исключает оценку из подсчёта. Среднее отдельных оценок
не является средним дневных рейтингов или формулой рейтинга площадки.

Свою оценку исключать по подтверждённому ID. При известной только дате
откладывать записи всех собственных дней отдельно, не выбирать случайную
пятёрку. Это также отложит чужие записи того же дня — сообщать явно.
Не заявлять, что все остальные записи доказанно независимы. Опубликованный
рейтинг карточки не очищать вычитанием 5: он может включать свою оценку.

## Рабочая команда Hermes — поручение владельца 28.10.2026

`python3 /home/hermes/.hermes/skills/productivity/msp-self-purchases/scripts/msp_rating_history_cli.py --marketplace wb --sku SKU --from YYYY-MM-DD --to YYYY-MM-DD --review-date YYYY-MM-DD --json`

Для Ozon — `--marketplace oz`. review-date брать из v_self_purchase.review_date
по точным marketplace/store/marketplace_sku (SQLite mode=ro). Остальные свои
даты передать повторным --own-review-date. Если review_date отсутствует,
не подставлять purchase_date: только запрос истории без --review-date.
from должен быть раньше review-date. Конец — не позже вчера по Москве;
на запрос «сейчас» показывать настоящую дату последнего наблюдения.
Равные контрольные окна сохраняет существующий планировщик. Просмотр до
последнего дня — отдельный режим; не скрывать разную длину периодов.

Прямые вызовы MCP:
1. account_limits; общий бюджет 24 чтения, включая проверку квоты.
2. WB: wb_sku(sku=int(SKU),report="comments") и
   wb_sku(sku=int(SKU),report="by_period",d1="YYYY-MM-DD",d2="YYYY-MM-DD").
3. Ozon: отдельный ozon_sku с теми же параметрами. comments — массив,
   не WB-объект. Отбор дат comments выполняется локально.
4. Нужны date, valuation, ID при наличии. Текст необязателен. Четыре
   счётчика с текстами НЕ условие доступности выборочной статистики звёзд.
5. Дневные снимки сортировать по data; rating/commentsvaluation WB хранить
   отдельно. no_data=1 Ozon и daynum=0 WB не являются наблюдениями.

Установлен только отдельный вход, не заменяющий прежний основной отчёт
msp_self_sku_report_cli.py. Службы, расписания и маркетплейсы не менялись.
Воспроизводимый установщик: scripts/install_msp_rating_history_helper.py
--source-commit SHA40. Он экспортирует согласованные файлы из конкретного
коммита в отдельную неизменяемую папку с manifest.json и SHA-256, без git pull.
Точный активный коммит, папка исходников и SHA-256 файлов указаны в
`/home/hermes/.local/share/msp/rating-history/active-manifest.json`.
Для новой установки выбирать проверенный коммит основной ветки; отдельный
манифест конкретной версии сохраняется в её неизменяемой папке.

Текущий доступ даёт датированные снимки и неполные выборки, а не гарантированно
все оценки. wb_sku и ozon_sku не взаимозаменяемы. WB rating может быть
округлён; commentsvaluation сохранять отдельно. Ozon no_data=1 — пропуск.
Полнота ежедневных снимков не равна полноте ленты оценок. Прямой публичный
WB дополнительно даёт ID и распределение, но требует nmId-фильтра внутри
imt-семейства. Текущие счётчики не переносить в прошлое.

Не требовать тексты или четыре счётчика с текстами для частичной статистики
звёзд. При этом не подставлять частичную выборку в готовые строгие формулы
как полный ряд. Реальные отзывы и данные компании не публиковать в GitHub.

Это правило выше старого RATING_RUNTIME_20261027 и требования «сначала
найти четыре ряда, иначе оценки недоступны». Старые строгие формулы
сохранены для будущих полных рядов, не блокируют доступные звёзды и рейтинг.
Подключение шести кабинетов продавца не условие работающих внешних методов.
