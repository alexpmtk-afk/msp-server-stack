## ПРИОРИТЕТНЫЕ ПОЛЯ MPSTATS 23.10.2026 — заказы, суммы и показатели выкупа

Используй строго датированный `wb_sku(report=full).period_stats` в том же MCP MPSTATS, который уже подключен, **не требуй новых источников** ради заказов. Внешняя аналитика MPSTATS в интерфейсе 2026 показывает поле `sales` как оценочные «Заказы, шт.», `revenue` как оценочную «Сумму заказов, руб.»; старые технические имена API сохранены. Показывай их отдельно для периода ДО/ПОСЛЕ каждого `review_date` из реестра. Это оценки парсинга остатков, **не независимо подтверждённые оплаченные органические заказы**; в них могут присутствовать и ранее записанные самовыкупы. `purchase`, `purchase_after_return`, `sales_estimated`, `revenue_estimated`, `lost_profit` сохраняй как отдельные буквальные показатели MPSTATS: без установленной единицы/смысловой модели не превращай их в реальное количество возвратов, оплат, выручку или прибыль. Не складывай `sales` с `sales_estimated`. Поля `orders` и отдельного числа возвратов в испытанном `wb_sku(full)` нет — `UNKNOWN`, а не ноль; это не значит, что этих показателей нет в других разделах MPSTATS. Ключевые модули: `mpstats_full_metrics.py`, `checkpoint_workflow.py`, `checkpoint_report_ru.py`, `self_purchase_analysis.py`. Прочитай `references/MPSTATS_EXPANDED_FIELDS_REAL_ACCEPTANCE_20261023.md` и семантику v11 `references/self_purchase_semantics_v11.yaml`. Реальные пробы [#573–575](https://github.com/alexpmtk-afk/msp-server-bridge/issues/575) подтвердили получение полей. Это ретроспективный анализ, без автоматического создания покупок/отзывов.

## Проверенная объединённая аналитика 23.10.2026 — MPSTATS + журнал цен + проверка экономики

## ГЛАВНОЕ ПРАВИЛО 23.10.2026 — ПОСЛЕ КАЖДОЙ ДАТЫ ОТЗЫВА, НЕ ТОЛЬКО ПОСЛЕ ПОСЛЕДНЕЙ

**Высший приоритет, явно утверждено владельцем 23.10.2026.** Читай `references/PER_REVIEW_CHECKPOINT_WINDOWS_20261023.md` (полный канон `docs/self-purchases/PER_REVIEW_CHECKPOINT_WINDOWS_20261023.md`) и `references/SERIES_TARGET_PER_ROW_CORRECTION_20261022.md`. Любая более старая инструкция ниже, допускающая только один итог после последнего отзыва, **УСТАРЕЛА для поэтапного отчёта**.

Сгруппируй `completed` записи по `marketplace/store/marketplace_sku`. `Кол-во выкупов` / `quantity` — один повторяющийся **план всей карточки**, не суммировать; `Дата отзыва` / `review_date` — **дата отдельной строки**, а не колонка количества. Сортируй даты: выдай отдельный контроль после **1-й, 2-й, 3-й и каждой последующей** записанной даты отзыва. Если в один день несколько записей — один календарный контроль с количеством записей дня.

База для каждого контроля: `N` суток **до самой первой даты отзыва**, текущий результат: `N` суток **после именно этой даты**; сам день отзыва исключён. `N=min(30, фактически завершённые дни после события, дни ДО следующего зарегистрированного отзыва)`. Не допускать попадания следующей даты отзыва в окно после предыдущего; если между ними нет полного дня — `POST_WINDOW_PENDING`. Если с последнего события меньше 30 дней, брать **одинаковый сокращённый период** ДО и ПОСЛЕ; `SHORTER_EQUAL_WINDOW_PRELIMINARY`. В день отсечки `as_of` свежий неполный день не включать. Оставить общее сравнение до первого/после последнего как **дополнительный итог**, не подмену всех последовательных контрольных точек.

Используй `series_analysis.analyze_series(...)["checkpoints"]` и `series_report.build_series_checkpoint_reports`, запрашивая MPSTATS **для каждой даты и окна отдельно**; не смешивай оценочные продажи, подтверждённые заказы и причинный эффект. Никаких действий по искусственным заказам или отзывам. При отсутствии кода на VPS — не заявляй, что он исполняется, даже если это правило уже добавлено в Skill.

## САМЫЙ ВЫСОКИЙ ПРИОРИТЕТ: серия, а не суммирование quantity (22.10.2026)

Источник `Кол-во выкупов` / raw SQLite `self_purchase.quantity` есть **ПЛАН на всю карточку**, повторяется для каждой строки. `quantity=5` в трёх строках не означает 15 купленных единиц — это **план 5, три зарегистрированных выкупа**, три записи о датах отзывов при заполнении полей. Группировать по `marketplace,store,marketplace_sku`; искать **первый и последний отзыв серии**. Измерять `T_first-N…T_first-1` против `T_last+1…T_last+N`, N=30 по умолчанию. При 3 из 5 можно сформировать обозначенный промежуточный отчёт, только по равным завершённым периодам; затем пересчитывать после следующих отзывов. Использовать `scripts/series_analysis.py` и `scripts/series_report.py` как **основной** путь анализа; прежние `purchase_unit_audit.py` и `case_report.py` — только устаревшие однострочные технические проверки и не могут давать общий вывод по серии. Не суммировать планы, не выдавать датированные строки реестра за независимо опубликованные пятизвёздочные оценки. Ошибочные архивные `136/92 единиц` помечены `SUPERSEDED_NON_ADDITIVE_QUANTITY`. Читай `references/SERIES_TARGET_PER_ROW_CORRECTION_20261022.md`. Предмет товара, цена, реклама, наличие, MPSTATS и подтверждение отзывов сохраняются как факторы/источники; никаких искусственных заказов или отзывов не создавать.

## ОБЯЗАТЕЛЬНОЕ ДОПОЛНЕНИЕ: количество единиц выкупа — отдельно от оценок (22.10.2026)

Для каждой завершённой строки из `v_self_purchase` сохраняй **`quantity`** как число выкупленных единиц; по карточке/периоду считай сумму единиц, не число строк. Владелец описал предположение «1 единица может дать 1 оценку 5», но без индивидуальных опубликованных датированных отзывов это НЕ число реальных оценок и не факт изменения общего рейтинга. Одна `review_date` или `review_url` для `quantity>1` не означает публикацию всех оценок в один день. Отдельно показывай известные единицы и независимо подтверждённые уникальные отзывы, даты публикаций и оценки. Без данных статус `UNKNOWN`, не выдавай неподтверждённые отзывы за органические. Сохраняется якорь сравнения T = дата отзыва, НЕ покупки, а исторический рейтинг требует подтверждённой даты. Ни при каких условиях не предлагай действия для искусственного создания заказов или недостоверных оценок.

## ПРИОРИТЕТНОЕ УТОЧНЕНИЕ ВЛАДЕЛЬЦА: 22.10.2026 — дата отзыва, не покупки

## Приоритет анализа, утверждённый 22.10.2026: MPSTATS-first

**Не требуй от владельца сначала изучать Google «_01_Продажи (новая)» или устанавливать WB/Ozon MCP.** Для ретроспективного анализа бери фактические завершённые события из SQLite `v_self_purchase`, по их `marketplace/store/marketplace_sku` запрашивай датированную историю MPSTATS `wb_sku` / `ozon_sku` при наличии тарифа.
