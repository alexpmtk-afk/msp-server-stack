# SIG-002 «Поднять цену» — семантика производственных заказов (аудит 27.10.2026)

**Статус 27.10.2026:** утверждённая владельцем семантика рекомендации SIG-002. Только чтение источников и объяснение; изменение цен запрещено. Прежнее текстовое сравнение SIG-002 — только исходная гипотеза. Любые отдельные товары, связанные с оружием или оружейными принадлежностями, исключаются из этого направления анализа и автоматизации.

## 1. Реальные источники на REMOTE

- Общая SQLite: `/opt/mcp/data/msp/msp_data.sqlite3`, режим чтения при анализе.
- `product_listing`: SKU карточки → **внутренний артикул**, ключ карточки `(marketplace,store,marketplace_sku)`. `marketplace_article` не заменяет числовой SKU, `product_name` не использовать для ключевого сопоставления.
- `production_sewing_order` (представление `v_production_sewing`) — швейка/маскировка; источник Google «ГЗП Маскировка | Швейка», вкладка «ГЗП МП/ОРК 25», `gid=666345199`. На 27.10.2026, 09:14 МСК: **714 текущих строк**, `642 ok / 72 review`, 6 строк без артикула; последняя повторная загрузка `unchanged=714` (состояние `partial` означает замечания к источнику, а не полный провал).
- `production_metal_order` (представление `v_production_metal`) — металлические изделия ЛМ/АНТ; источник Google «МП Загрузка производства АНТ и ЛМ», вкладка «Загрузка ЛМ/АНТ», `gid=1990590773`. 26.10.2026 17:11 МСК: **730 текущих строк**, `346 ok / 384 review`, 14 без артикула; **металл не имеет утверждённого ежедневного расписания обновления**. Перед каждой интерпретацией проверять свежесть `production_import_run`.
- Источник схем и нормализации: `msp-server-stack/apps/msp_production_sync/sync.py` и `config/msp-data/semantics/production_{sewing,metal}.yaml`. История загрузок — `production_import_run`, изменения строк — `production_row_revision`, ошибки источника — `production_data_issue`.

## 2. Оригинальные колонки швейки (A:K)

| Исходная колонка | SQLite | Что означает / как использовать |
|---|---|---|
| A «Заказчик» | `requester` | Кто инициировал производственный заказ (например, МП/РП). **Не** маркетплейс, кабинет и **не** фактическое производство. |
| B «Артикул» | `internal_article` | Внутренний артикул заказа. Главный ключ поиска после преобразования SKU через `product_listing`. |
| C «Название товара» | `product_name` | Подпись для человека, не первичный ключ. |
| D «Кол-во» | `requested_qty_raw/decimal` | Заказано производству. Пустота = неизвестно, не ноль. |
| E «Отдали Факт» | `delivered_qty_raw/decimal` | Указанное производством фактически переданное количество. Само по себе **не доказывает**, что единицы уже приняты на нужный склад маркетплейса. |
| F «Дата размещения заказа» | `placed_at_raw/iso` | Когда размещён заказ; **не** дата ожидаемого прихода. |
| G «N заказа» | `order_number` | Идентификатор заказа **текстом**, может повторяться для разных товаров, иметь суффиксы `/1`, `/2`. Не уникальный ключ строки. |
| H «Желаемый срок» | `desired_at_raw/iso` | Запрошенная желательная дата; **не подтверждена производством автоматически**. |
| I «Подтвержденный срок» | `confirmed_at_raw/iso` | Сообщённый подтверждённый срок; для прогноза важнее H, но **не гарантия фактического поступления**. |
| J «Комментарий для внеплановых договоренностей» | `comment_text` | Ручные пояснения, переносы, изменения условий; их нельзя игнорировать при конфликте со сроками. Не превращать свободный текст в новую дату без проверки. |
| K «Ответственный» | `responsible` | Контакт по заказу, не срок поставки и не статус выполнения. |

**Отдельной колонки «Осталось» в швейке НЕТ.** Остаток выводится из D и E; пустое E = 0 фактически передано. Проверять несколько строк заказа и повторные записи, не удваивать. **Если E «Отдали Факт» пусто, считать фактически переданным 0 шт.** При корректном D непереданный остаток `max(D−E,0)`. Если D отсутствует или некорректно — уточнить количество. Перевыполнение E>D допустимо: остаток 0, не отрицательный. Не считать заказ «активным» только потому, что есть I.

## 3. Оригинальные колонки металла (A:M)

| Исходная колонка | SQLite | Что означает / как использовать |
|---|---|---|
| A «А» | `requester` | Заказчик/инициатор (например, МП). Не тип маркетплейса. |
| B «Производство» | `production_site` | Площадка, например ЛМ/АНТ. |
| C «Артикул» | `internal_article` | Внутренний артикул. |
| D «Название товара» | `product_name` | Справочная подпись. |
| E «Кол-во» | `requested_qty_raw/decimal` | Заказано. |
| F «Приняли Факт» | `delivered_qty_raw/decimal` | Количество, обозначенное источником как фактически принятое. Не приравнивать автоматически к складу WB/Ozon. |
| G «Осталось» | `remainder_qty_raw/decimal` | Вычисляемая/ручная колонка с возможными ошибками; **не использовать как первичный остаток**, считать `max(E−F,0)`. Пустая F «Приняли Факт» = 0; при конфликте с G фиксировать расхождение. |
| H «Дата размещения заказа» | `placed_at_raw/iso` | Дата заказа. |
| I «№ накладной» | `invoice_number` | Номер документа передачи, часто пустой; сам номер не является доказательством прихода на МП. |
| J «№ заказа» | `order_number` | Идентификатор заказа — текст, может повторяться между строками и изделиями. |
| K «Желаемый срок» | `desired_at_raw/iso` | Желаемая дата, не подменять подтверждённым сроком. |
| L «Комментарий» | `comment_text` | Договорённости, перенесённые даты, уточнения и иные исключения; читать перед решением. |
| M «Подтвержденный срок» | `confirmed_at_raw/iso` | Подтверждённый срок, более сильный ориентир, но не факт поставки. |

В проверке 27.10.2026 найдены **2 расхождения** G с разницей E−F. Для анализа использовать проверенные E и F, а G отмечать как ошибку источника; не менять исходную таблицу.

## 4. Служебные поля обеих SQLite-таблиц

Нормализованные даты схемы SQLite: `placed_at_iso` — дата размещения,
`desired_at_iso` — желаемая дата, `confirmed_at_iso` — подтверждённая.
Это дополнения к исходным `*_raw`, не замена исходного текста; NULL не
разрешает придумывать дату. Чтение этих данных не является разрешением изменять цены.

- `source_row`: **физический номер** исходной строки, не устойчивый ID заказа; перестановка строк даёт новую ревизию. Не агрегировать автоматически по одному номеру заказа или артикулу.
- `*_raw`: буквальный текст исходной ячейки, включая даты `7.10.25`, `30.10.25`, пустые значения, форматы чисел и комментарии. Не уничтожать.
- `*_decimal`: число из исходного количества, не подтверждение поставки на WB/Ozon. Для пустых фактических E/F семантика SIG-002 — 0 переданных от производства.
- `*_at_iso`: дата YYYY-MM-DD, только когда исходная дата однозначно распознаётся с **полным четырёхзначным годом**. `DD.MM.YY` и `DD.MM` могут остаться с `NULL` ISO из-за ограничений загрузчика; **читать `*_raw`**, двухзначный год интерпретировать при однозначности (например, 25 → 2025). Для даты без года не придумывать год: при неоднозначности отмечать сомнение.
- `data_quality` (`ok` / `review`) и `issues_json`: сообщения о пропусках и неоднозначностях; `review` не означает, что весь заказ ложный, но не позволяет использовать спорное поле без проверки.
- `raw_cells_json`: массив оригинальных A:K или A:M, необходим для проверки нестандартных значений и схемы.
- `row_sha256`, `first_observed_at`, `last_changed_at`, `last_seen_run`: журнал синхронизации, **не** даты получения товара.
- `is_current`: строка присутствует в последнем успешном снимке; `1` не означает, что заказ незавершён. Старая запись после удаления из текущего источника сохраняется с `is_current=0`. Не брать её как текущую поставку.
- `production_row_revision`: изменение прежних значений того же `source_row`. Физическая строка не является неизменяемым бизнес-ID — осторожно при вставке/перестановке строк.

Даты и числа проверяются независимо. Состояние импорта `partial` сопровождается качественными замечаниями, в том числе к укороченным датам: 72 строк швейки и 384 металла требуют review. Сигналы в них не следует полностью игнорировать, но при использовании спорного поля помечать неопределённость.

## 5. Как правильно сопоставлять SKU маркетплейса с заказом

1. Из сигнала SIG-002 читать **каждую карточку отдельно**, числовой SKU из `(123456789)` / `(Арт. 123456789)`, дни покрытия `_N`, дату поступления, если есть. Не переносить дату и дни из соседнего товара.
2. В `product_listing` искать `marketplace_sku = ?`. Канонический ключ карточки — `marketplace + store + marketplace_sku`; если в сигнале нет маркетплейса/магазина, найти **все** соответствия этого SKU, а не угадывать нужный кабинет.
3. Объединять найденные записи только если после проверки они дают **один и тот же однозначный `internal_article`**. При разных внутренних артикулах — статус `НЕОДНОЗНАЧНО: требуется сопоставление`, без автоматического ценового совета. Числовой SKU не равен внутреннему артикулу.
4. Искать `internal_article` среди **текущих** строк обоих производств, нормализуя регистр и крайние пробелы для надёжного сопоставления. Не объединять разные суффиксы/варианты изделия по названию или приблизительной похожести.
5. У одного артикула может быть много строк заказов, разные предприятия, номера, сроки, степени исполнения. Сопоставление нельзя завершать на первой строке и нельзя складывать весь исторический объём заказа как будущее поступление.
6. Сохранять источник, исходный `source_row`, даты, количество и качество каждого возможного заказа в обосновании решения. При отсутствии совпадения по производствам не утверждать «не заказан» без проверки свежести загрузок и полноты сопоставления.

На 27.10.2026 в `product_listing` **1562 записи**, 32 без внутреннего артикула; по текущим производственным каталогам нашлось совпадение для 706 записей, **856 не совпало** (включая позиции без подтверждённых заказов и отсутствующих в каталогах). Из найденных 706 у **507** более одной строки производства. Это не количество уникальных товаров и не процент покрытия номенклатуры; считать следует по ключу карточки и отдельно по внутреннему артикулу. Среди 1560 уникальных числовых SKU не найдено случаев с разными внутренними артикулами, но проверки неоднозначности нельзя убирать.

Реальный сигнал 27.10.2026 №2770: все 4 SKU сопоставились с внутренними артикулами, у них соответственно 2, 9, 6 и 5 текущих производственных строк. Это **не** значит, что каждая строка ещё ожидается.

## 6. Решение SIG-002 — бизнес-правила 27.10.2026 (приоритет над 09.10)

**Сначала сообщение, затем реальное производство.** Для каждой карточки SIG-002 отдельно взять её числовой SKU и **уже рассчитанное самим сигналом** количество дней обеспеченности `_N`. Не пересчитывать продажи, не собирать текущий остаток из случайных Google-таблиц и не складывать WB с Ozon. Если для дополнительного подтверждения факта FBS действительно нужен остаток, читать актуальные остатки 1С через авторизованный QRsite, не старые расчётные таблицы. Отсутствие даты производства в Telegram **не означает отсутствие заказа**.

Алгоритм:
1. Выделить карточку и её `_N`/дату строго из собственного блока `Товар N:` (включая переносы строк), установить сигнальную дату в МСК. При отсутствии точного SKU или `_N` — `УТОЧНИТЬ`. Владелец подтвердил, что `_N` уже вычислен системой по конкретной карточке; считать его готовым исходным показателем.
2. По `product_listing` получить единственный `internal_article` для карточки (учитывая `marketplace` и `store`); для других карточек того же товара отдельные дни `_N`, не смешивать их. При расхождении соответствий — `УТОЧНИТЬ`.
3. Только для `requester=МП` получить **все** `is_current=1` строки по артикулу из двух таблиц: швейка `production_sewing_order` и металл `production_metal_order` (ЛМ и АНТ). `РП` и `ОРК` — не учитывать. Проверить свежесть `production_import_run`. Исторические выполненные заказы не являются будущими партиями. Проверить возможные дубли одного изделия в одном заказе; разные заказанные партии не сливать.
4. Количества: швейка заказано D, «Отдали Факт» E; металл заказано E, «Приняли Факт» F. **Пустая фактическая ячейка = 0**, НЕ `UNKNOWN_QTY`. Оставшееся `max(заказано−передано,0)`. Отрицательных остатков нет, сверхпередача может быть фактом. Металлическая G «Осталось» ненадёжна и никогда не перебивает расчёт по E/F. Если само заказанное количество отсутствует — только эту строку отметить `УТОЧНИТЬ`, не игнорировать остальные.
5. Даты: швейка I, металл M — плановые подтверждённые сроки передачи **на собственный склад**. H/K — желательные сроки, не подменяют подтверждённые. В комментарии J/L искать: отмену/«не будут производить» (исключить будущую поставку), более поздний перенос срока (взять обновлённую дату), частичные партии с разными датами (учитывать каждую по очереди), брак/задержку. Комментарий о браке у производителя не уменьшает уже переданный факт и сам по себе не создаёт долг. При полном исполнении строки исторические планы и комментарии не создают будущих поступлений.
6. Сигнальная граница обеспеченности = дата сигнала по МСК + `_N` календарных дней по принятой трактовке; не пересчитывать спрос. Если **есть положительная незавершённая партия с достоверным сроком не позже этой границы** — `НЕ ПОДНИМАТЬ`. Не рассчитывать доставку до FBO Ozon: по согласованной модели Ozon отгружает ежедневно по FBS с собственного склада. **Не выполнять отдельный пересчёт спроса или прогноз «успеет на Ozon»**. Если все достоверные будущие партии позже границы или отсутствуют при свежих, однозначных данных — `ПОДНЯТЬ` как рекомендация по обычному товару. Если единственные незавершённые партии просрочены/без однозначной даты и вывод зависит от них — `УТОЧНИТЬ`, но не объявлять их гарантированным приходом.
7. **Бизнес-исключение выше механического сигнала**: если уполномоченный владелец или действующий авторитетный источник подтвердил распродажу/снятие товара с ассортимента, результат `НЕ ПОДНИМАТЬ` даже при отсутствии будущего производства. Не домысливать такую распродажу из отсутствия заказов и не выдавать неподключённую таблицу за источник.
8. На вопрос о результате отвечать кратко: `SKU | ПОДНЯТЬ / НЕ ПОДНИМАТЬ / УТОЧНИТЬ | причина (дни по сигналу; незавершённая партия, дата; бизнес-исключение)`. Отдельно при необходимости показать строки заказов и комментарии. При спорном поле помечать только действительно влияющую на вывод неопределённость, не задавать владельцу очевидные вопросы.

**Приоритет:** эти правила заменяют взаимоисключающие инструкции от 09.10.2026 «нет даты в Telegram ⇒ не заказан» и требование независимо пересчитывать покрытие/логистику до склада Ozon. Не путать фактическую передачу производства на свой склад с фактическим остатком FBS — для решения используем `_N` сигнала. Изменение цен, заказов, FBS, Telegram, сервисов или ежедневных заданий из этого документа **не разрешается**.

### Контрольные бизнес-примеры

- Ozon `3721851671`, переплётный станок, сигнал от 27.10.2026 `_9`: производственные заказы ЛМ № ЛУУН-000258 (38 шт., 29.10.2026, передано 0) и № ЛУУН-000298 (76 шт., 23.11.2026, передано 0). **НЕ ПОДНИМАТЬ**: первая партия 29.10 раньше 9-дневной границы; не просчитывать FBO и продажи.
- WB `366748699`, держатель соусов: в производственных строках новых ожидаемых партий нет; механически получалась рекомендация «поднять», **но владелец 27.10 подтвердил распродажу и прекращение производства — НЕ ПОДНИМАТЬ по ручному бизнес-исключению**. При эксплуатации проверять сохранение статуса исключения через авторитетное решение/источник; не считать распродажей все товары без заказа.
- Строка производства `UW-2801`: есть заказ и нет фактической передачи, но комментарий «не будем производить» — **не считать будущим поступлением**.
- Металл, кронштейн PS5: комментарий о 50% на 12.01 и 50% на 16.01 создаёт две даты только когда эти партии **ещё не переданы**; при равном заказанном/факте ожидаемых партий нет.
- Металл, подставка под виниловые пластинки: 46/46 передано, замечание о 34 шт. брака у производителя **не уменьшает факт**.

**Данные и действия:** только чтение SQLite; без фактического изменения цен. Если источник устарел, нет соответствия товара или спорная дата влияет на решение — `УТОЧНИТЬ`. Отсутствие отдельного согласованного автоматического ценового исполнителя не мешает Hermes выдавать обоснованный совет.
