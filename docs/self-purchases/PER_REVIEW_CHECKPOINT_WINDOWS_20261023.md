# МСП Самовыкупы — обязательный анализ после КАЖДОГО отзыва (23.10.2026)

**Статус: утверждённое владельцем исправление**, приоритет над единственным сравнением «до первого / после последнего». Не изменять исходные замороженные материалы совещания. Ретроспективная аналитика без автоматизации фиктивных заказов и отзывов.

## Два разных столбца

- **`Кол-во выкупов` → `self_purchase.quantity`**: общее запланированное число событий на карточку (например, 5), повторённое в каждой строке. Это НЕ количество отдельного выкупа и нельзя `SUM(quantity)`.
- **`Дата отзыва` → `self_purchase.review_date`**: дата записанного отзыва **по конкретной строке**. НЕ содержит число запланированных выкупов. Публикация и оценка на площадке независимо не подтверждены.
- Каждая завершённая строка (`completed`) — одно зарегистрированное событие; плановые записи не включать. Группировка `marketplace, store, marketplace_sku`.

## Обязательный новый порядок

1. Отсортировать все непустые `review_date` одной карточки. После **первого, второго, третьего и каждого следующего** датированного события выдавать самостоятельную контрольную точку с числом накопленных записанных отзывов и количеством завершённых строк относительно плана. Если несколько отзывов записаны на один календарный день — одна временная контрольная точка с количеством записей этого дня: показатели продаж внутри суток не отделяются друг от друга.
2. За базовый период **ДО** принять `N` завершённых суток непосредственно **перед самой первой датой отзыва**.
3. За очередной период **ПОСЛЕ** принять `N` завершённых суток непосредственно **после даты текущей контрольной точки**.
4. `N = min(30, прошедшие полностью завершённые дни после текущего события, дни до следующей записанной даты отзыва)`. Если следующий отзыв случился раньше 30 дней, **не включать** его дату и последующий период в результат после предыдущего события. Защита от ложной атрибуции последующих событий ранним.
5. Если прошло меньше 30 дней — брать **одинаковое сокращённое число дней** до первой даты и после рассматриваемой даты; статус `SHORTER_EQUAL_WINDOW_PRELIMINARY`. Сам день отзыва исключать. Дата `as_of` означает текущий незавершённый день, не включать её в «ПОСЛЕ».
6. Если после события нет ни одного завершённого календарного дня (например, два отзыва в соседние дни), ставить `POST_WINDOW_PENDING`; **не сравнивать** 0 дней с 30 и не приписывать эффекту нули продаж.
7. Повторять для всех контрольных точек. Ранее существовавшее «30 дней до первого против 30 дней после последнего» **можно сохранять как отдельный общий итог серии**, но его недостаточно и он не подменяет промежуточные этапы. В итоговом отчёте должны отображаться обе формы.

## Проверенный датированный пример из исходного реестра

**WB/laser**, план по карточке 5, зарегистрированы три даты: **05.08.2026**, **07.08.2026**, **18.08.2026**. Для даты отсечения 22.10.2026 и запроса 30 суток:

| После какой записанной даты | Накопленно записанных отзывов | Равный период ДО первого отзыва | Равный период ПОСЛЕ этой даты | Дней на сторону |
|---|---:|---|---|---:|
| 05.08.2026 | 1 | 04.08 | 06.08 | 1 |
| 07.08.2026 | 2 | 26.07–04.08 | 08.08–17.08 | 10 |
| 18.08.2026 | 3 | 06.07–04.08 | 19.08–17.09 | 30 |

Первая точка ограничена вторым событием, вторая — третьим. Это примеры **календарных окон**; таблица не содержит выдуманных показателей продаж или доказательств влияния отзывов.

Если анализ третьего события сделан **27.08.2026**, то доступно только **8 завершённых дней** после 18.08: **19–26.08**, и базовый период должен тоже состоять ровно из 8 дней: **28.07–04.08**.

## Обязательные проверки каждого отдельного отчёта

- Запрашивать MPSTATS за точные рассчитанные даты **отдельно для каждой контрольной точки** и проверять `d1/d2` ответа. Нельзя подставить один отчёт за последние 30 дней ко всем событиям.
- Не называть оценочные продажи MPSTATS верифицированными оплаченными заказами или органическими продажами.
- Отдельно учитывать доступность товара, движение цен, рекламу, качество, рынок и возможное изменение общей ситуации между событиями. Сопоставление ДО/ПОСЛЕ не доказывает причинного действия зарегистрированного отзыва.
- Неполная серия `3 из 5` уже допускает три самостоятельные контрольные точки, но план `5` не означает, что отзывы опубликованы.
- При отсутствии данных показывать статус `UNKNOWN` / `MPSTATS_WINDOWS_INCOMPLETE`, не придумывать цифры.

## Где реализовано

- Семантика: `config/msp-data/semantics/self_purchase.yaml` → `review_checkpoint_analytics`.
- Расчёт: `apps/msp_self_analytics/series_analysis.py` → `checkpoints`; старые `windows` сохранены как общий итог для совместимости.
- Привязка конкретных показаний MPSTATS: `apps/msp_self_analytics/series_report.py` → `build_series_checkpoint_reports`; принимает отдельные `before/after` для каждой точки.
- Автоматические тесты: `tests/test_msp_self_review_checkpoints.py`.
- Skill Hermes: `apps/hermes/msp_self_purchases_skill/SKILL.md` → высший приоритет этой инструкции; после синхронизации на VPS нужно подтвердить SHA и реальное чтение агентом.
- После code review/CI — обновление Hermes через владельцем разрешённую bridge-процедуру; копия в GitHub сама по себе не равна установке в Hermes.
