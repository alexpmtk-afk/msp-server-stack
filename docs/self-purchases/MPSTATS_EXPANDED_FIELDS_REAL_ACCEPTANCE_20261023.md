# MSP-SELF — расширенные показатели MPSTATS для каждого периода, 23.10.2026

## Реально проверенный источник

Два read-only прогона `wb_sku(report="full")` на VPS [№573](https://github.com/alexpmtk-afk/msp-server-bridge/issues/573), [№574](https://github.com/alexpmtk-afk/msp-server-bridge/issues/574) подтвердили 26 имён полей `period_stats`. В обоих периодах числовые `sales`, `revenue`, `days_in_stock`, `purchase`, `purchase_after_return` были доступны. Нет самостоятельных `orders`, `orders_sum`, `returns`, `return_amount` в этом **конкретном** методе, а не в MPSTATS вообще.

Согласно официальным обновлениям [MPSTATS, май 2026](https://mpstats.io/media/mpstats/news/produktovye-obnovlenija-za-maj-2026-goda), во внешней аналитике ранее называвшиеся «Продажи» и «Выручка» метрики стали именоваться «Заказы (шт.)» и «Заказы (руб.)». **Ключи API остаются `sales` и `revenue`** в доступном ответе `wb_sku(full)`. Это оценки парсинга остатков, не гарантированная оплата и не органические покупки: [официальное объяснение MPSTATS](https://wiki.mpstats.io/ru/FAQ/Продажи_и_заказы/Почему_расходятся_данные_в_личном_кабинете_и_во_внешней_аналитике_MPSTATS). **Нельзя** делить их на «органические» и «самовыкупы» без отдельного подтверждения.

## Контракт метрик без двойного учёта

| Поле API | Как использовать в нашем отчёте |
|---|---|
| `sales` | Внешняя оценка заказов, шт. (старое техническое имя); НЕ подтверждённые реальные оплаты |
| `revenue` | Внешняя оценка суммы заказов, руб. (старое техническое имя); не фактические выплаты |
| `days_in_stock` | Дни наличия; отдельно отмечать несопоставимость общего объёма при разных днях |
| `sales_estimated`, `revenue_estimated` | Дополнительные оценочные поля MPSTATS; не заменяют и не складываются с `sales/revenue` |
| `purchase`, `purchase_after_return` | Сохранять числовое значение с **буквальным именем** и пометкой `UNIT_UNVERIFIED`; НЕ трактовать как количество выкупов/возвратов |
| `lost_profit` | Дополнительный расчёт провайдера; не доказанный финансовый ущерб |
| `orders`, `return_count` | `UNKNOWN` для `wb_sku(full)` этого теста, а не ноль |

Нельзя считать `sales` и `sales_estimated` двумя независимыми категориями фактических заказов, складывать их, или вычислять реальные возвраты из `purchase - purchase_after_return`. Исторические рейтинги на эти даты не подтверждены.

## Реальная аналитика по уже зарегистрированной истории

[Проверка №575](https://github.com/alexpmtk-afk/msp-server-bridge/issues/575): на одном WB SKU из существующего SQLite выполнены **6** датированных запросов, по каждой паре ДО/ПОСЛЕ первого, второго, третьего реестрового отзыва. Все 6 ответов структурированные; план 5, завершённых строк и дат отзывов 3.

| Отзыв (по реестру) | Дней ДО и ПОСЛЕ | `sales` (оценочные заказы) | `revenue` (оценочная сумма) | `purchase` | `purchase_after_return` |
|---|---:|---|---|---|---|
| 05.08.2026 | 1 | 0 → 0 | 0 → 0 | 75 → 75 | 74 → 74 |
| 07.08.2026 | 10 | 0 → 0 | 0 → 0 | 75 → 75 | 74 → 74 |
| 18.08.2026 | 30 | 0 → 3 | 0 → 43 041 | 75 → 75 | 74 → 74 |

По дополнительным модельным полям MPSTATS `sales_estimated` за последовательные интервалы составляет 0→0, 7→5, 11→2, `revenue_estimated` соответственно 0→0, 101018→73096, 156120→28194. **Эти модельные значения не подменяют наблюдаемые `sales/revenue`, не прибавляются к ним и не обосновывают эффект отзывов.** На 30-дневном окне дни наличия различались (26→30). В журнале цен было 1 событие в полном базовом периоде; причинные выводы невозможны.

## Где добавлено

- `apps/msp_self_analytics/mpstats_full_metrics.py` — строгая схема, пропущенные поля как `None`, запрет преобразования `purchase` в штуки/денежные возвраты.
- `checkpoint_workflow.py` — только **после** проверки источника и точных дат дополнительно связывает показатели с каждой контрольной точкой.
- `checkpoint_report_ru.py` — показывает и суммы, и дополнительные поля, с объяснениями неопределённости.
- `tests/test_msp_self_mpstats_full_metrics.py` — пропуски, неверные типы, дубли, случайные даты и исключение причинных выводов.
- Частный сценарий `scripts/remote/msp_self_all_checkpoint_live_20261023.py` передаёт эти поля из реального `period_stats`, без модификации SQLite.
- `config/msp-data/semantics/self_purchase.yaml` → `mpstats_external_metrics`.

Ограничения: испытано на WB и `wb_sku(full)`. API другого отчёта или Ozon может возвращать иной набор полей. Не подключать новые кабинеты только из-за недостающей колонки. Не делать скрытых, искусственных или неаутентичных заказов или отзывов. Это анализ уже записанной истории.
