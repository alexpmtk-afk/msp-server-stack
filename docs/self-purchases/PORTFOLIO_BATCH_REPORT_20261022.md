# МСП Самовыкупы — пакетный отчёт по существующим карточкам (22.10.2026)

## Назначение

После проверенного единичного случая с урной (приватный протокол #552, русская приёмка #557) расчёт можно повторять для нескольких карточек **без изменения исходных данных, без действий на маркетплейсах и без причинных утверждений о влиянии отзывов**.

Модуль: `apps/msp_self_analytics/batch_report.py`.
Функции: `plan_portfolio`, `build_portfolio_report`, `card_key`.

## Сверка с неизменяемым первоисточником

Перед расширением аналитики агент должен прочитать:
1. Приватные первоисточники: `msp-server-bridge/docs/self-purchases/original/MEETING_TRANSCRIPT_2026-10-21.md` и `INITIAL_VISION_V1_2026-10-21.md`.
2. Действующий `PROJECT_COMPASS.md` и `DECISIONS_AND_DEVIATIONS.md`, а также уточнение владельца `SERIES_TARGET_PER_ROW_CORRECTION_20261022.md`.

**Соответствие замыслу:** данный слой относится к MSP-SELF-04 (исторические случаи); он предоставляет фактическую основу для MSP-SELF-03 (сопоставимые конкуренты), MSP-SELF-05 (сценарии) и MSP-SELF-06 (экономика). Это **не** законченный прогнозист: здесь ещё нет независимой оценки качества товара, рекламных затрат, сопоставимых аналогов или расчёта прибыли. Отсутствие этих сведений нельзя выдавать за нулевые значения.

Обсуждавшиеся на совещании соотношения 90/5/5 и 80/20 — **оценки участников**, а не обученные коэффициенты и не исходные параметры модели. Нельзя выводить решение о следующем самовыкупе из успеха отдельной карточки; пассивная ретроспективная аналитика не должна становиться механизмом фиктивных заказов или искусственных оценок.

## Действующая бизнес-семантика

- Уникальность карточки: строго `(marketplace, store, marketplace_sku)`; разные магазины и площадки не смешиваются.
- Один завершённый ряд SQLite = один записанный выкуп. `quantity` — **повторяющийся план всей карточки**, а не число купленных штук. Не суммировать.
- Дата отзыва в реестре — заявленная дата события, **не** независимое подтверждение публикации или звёздности.
- Базовое окно: N завершённых суток **до самой ранней даты отзыва**. Последующее окно: N завершённых суток **после последней записанной даты отзыва**. Не считать дни появления отзывов и день проведения проверки.
- При нехватке 30 суток использовать только равные короткие окна, сообщая о предварительности.
- Не подменять отсутствующие данные MPSTATS нулями и не использовать текущий рейтинг в качестве исторического.

## Контролируемый порядок

1. Получить **только для чтения** завершённые строки `v_self_purchase` с ключом карточки, датами и полем плана, не экспортируя персональные сведения.
2. Выполнить `plan_portfolio(rows, as_of="YYYY-MM-DD", requested_days=30, max_cards=20)`. Это полностью локальная функция, без сети.
3. Обрабатывать **только** записи со статусом `READY_FOR_MPSTATS`. `RECONCILIATION_REQUIRED`, `INVALID_SERIES`, `NO_RECORDED_REVIEW_DATE`, `POST_WINDOW_PENDING` не создают запросов MPSTATS. План ограничен **двумя периодами на карточку** и максимум **20 карточками** за один вызов; меньший лимит допустим.
4. До каждого внешнего запроса проверять допустимую квоту MPSTATS и при ошибке сохранять явный статус. Не запускать бесконтрольные повторы.
5. Для каждой допустимой карточки собрать два словаря MPSTATS с фактическими `request_status`, `d1`, `d2`, `sales`, `revenue`, `days_in_stock`. Поставщик вызывается вне аналитического модуля.
6. Сохранить результаты во внутреннем словаре по ключу `card_key((marketplace,store,marketplace_sku))`: `{"before": result_before, "after": result_after}`. Передать его в `build_portfolio_report`. При несоответствии дат данные отвергаются.
7. Русские отчёты получать из `cards[].text_ru`. Итоговая `summary` отдельно считает полные данные, недостающие источники, конфликты, отсутствие дат отзывов, ожидание периода и ошибочные серии. Публиковать во внешние журналы только агрегаты и обезличенную диагностику; исходные ключи карточек и отзывы там не размещать.

## Границы текущего изменения

Это **расчётный пакетный слой**, а не автоматический сборщик из SQLite/MPSTATS, фоновый сервис или Telegram-бот. Серверный адаптер должен подключаться отдельно после проверки кодов и источников на реальной выборке (1–3 карточки), с ограничением запросов и без изменений Gateway, реестра и товаров. В частности, сам факт работы отчёта **не доказывает** реальное появление независимых публичных отзывов или причинность динамики продаж.

Применять вместе с `SERIES_TARGET_PER_ROW_CORRECTION_20261022.md` и `URN_SERIES_30DAY_MPSTATS_ACCEPTANCE_20261022.md`. Старый `case_report.py` остаётся только для технических однострочных проверок.
