**Дата:** 26.10.2026. **Решение владельца:** пока НЕ планировать привязку рекламного кабинета ради исторического анализа. Исследовать уже подключённый MCP MPSTATS и возможности **внешней аналитики по одному WB SKU**, без дополнительных кабинетов/токенов.

## Реально доступные данные без рекламного кабинета

### 1. `wb_sku(report=search_stats)` — внешняя видимость поиска

Метод вернул `PASS_STRUCTURED` за оба заявленных окна; обнаружены отдельные рекламные показатели:
`search_ad_visibility` **9 → 27**, `search_ad_position_avg` **81 → 113**,
`search_words_in_ad` **13 → 51**, `wb_count_in_ad` **0 → 0**,
а также `search_visibility` **9 → 27**, `search_position_avg` **86 → 122**, `traffic` **127.84 → 0**.

**Ограничение:** метод не вернул независимого эха границ периодов в теле результата. Бизнес-единицы `search_ad_visibility` и `traffic`, а также потенциально противоречивые `wb_count_in_ad=0` при ненулевых остальных рекламных полях **не верифицированы**, не считать эти числа показами, оплаченной рекламой или фактом расходов. Сначала уточнить контракт показателей и дат.

### 2. `wb_sku(report=keywords)` — рекламные и органические поисковые позиции

В реальном ответе `PASS_STRUCTURED` присутствовали `avg_ad_position`, `avg_organic_position` и вложенные поля `ad_type`, `cpm`, `ad_position`, `organic_position` по запросам. Верхний `total` = **14 ДО**, **51 ПОСЛЕ**. Адаптер первого этапа не смог извлечь датированные строки из полученной вложенной структуры (`query_rows=0`), **это ошибка неполной обработки структуры, НЕ отсутствие запросов/рекламного присутствия**. Следующий шаг: независимо проверить формат `data` и `dates` и затем дату/вид поля для каждого наблюдения без выгрузки текста поисковых запросов.

### 3. `wb_shelves(report=stats/items)` — рекомендательные полки

Это внешний инструмент; работает для любого SKU и **не требует** рекламного кабинета. Для каждого товара-хоста доступны `positions[date].position`, `ads` и `cpm`. `ads=1` — признак платного размещения **в рекомендательной полке**, а не всей рекламы товара. `wb_shelves(report=stats)` возвращает оценку числа карточек-хостов и видимости; `visibility_count` означает наблюдение по хосту за день, **не показы пользователям**. `sales/revenue` в этом методе относятся к **карточкам-хостам**, а не заказам анализируемого SKU.

| Контрольный показатель | ДО (31 д.) | ПОСЛЕ (31 д.) |
| --- | ---: | ---: |
| Карточки-хосты из `stats.items` | 3 | 134 |
| `stats.visibility_count` (хост-дни) | 3 | 179 |
| В `items`: просмотрено карточек-хостов / объявлено всего | 3 / 3 | 134 / 134 |
| Наблюдаемых дат размещения | 3 | 21 |
| Фактические строки `positions[date]` в выбранных границах | 3 | 177 |
| `positions[date].ads=1` в просмотренных записях | 0 | 0 |
| `stats.avg_cpm` | 0 | 0 |
| `stats.avg_position` | 88.67 | 65.93 |

Условия: вся пагинация `items` подтверждена для обоих окон (`all_host_cards_scanned=true`), все распознанные даты внутри соответствующих границ, но `visibility_count=179` и 177 детальных строк ПОСЛЕ **не тождественны** — смысл/полноту детализации нужно дополнительно проверить. Ноль платных признаков в полках **не доказывает отсутствие платного продвижения в поиске или других местах WB**. Запретить причинные выводы из роста количества хостов.

## Отдельный модуль «Внешняя реклама»

По [официальной справке MPSTATS](https://wiki.mpstats.io/ru/Плагин_Chrome/Плагин_в_карточке_товара), в платформе существует отслеживание внешних публикаций и трафика за последние 90 дней. Однако среди исследованных инструментов нашего MCP из 108 зарегистрированных пока **не установлен прямой read-only метод**, возвращающий отчёт этого модуля именно по SKU. Возможности веб-интерфейса/плагина **не равны** наличию MCP API. Не обещать агенту получение расходов на внешнюю рекламу без подтверждения метода.

## Вывод для текущего проекта

**Подтверждено:** MPSTATS MCP без рекламного кабинета способен отдать внешние **наблюдения видимости в поиске и рекомендательных полках** за исторические окна. По проверенной карточке резкое увеличение видимости после записанной даты отзыва совпало с ростом оценочных заказов, но это **наблюдаемая корреляция**, которая сама может объясняться изменениями ранжирования, спроса, конкуренции, наличия, цены и другими событиями.

**Не подтверждено:** расходы рекламного кабинета, реальные рекламные клики, покупки непосредственно из рекламы, каузальный эффект отзыва/самовыкупа, фактические оплаченные органические продажи, окупаемость.

**Приоритет следующего исследования без привязки кабинета:** расшифровка `wb_sku(keywords).data/dates`, единиц поисковых рекламных полей, проверка дат и стабильности на нескольких иных исторических SKU. Только затем обсуждать интеграцию **отдельного, источнико-ограниченного блока «Рекламная видимость по внешней аналитике»** в русский отчёт. Приоритет в коде сейчас остаётся за `v_price_history` и проверенным `wb_sku(full)` для заказов/наличия; эту внешнюю видимость НЕ превращать в рекламные расходы.

**Никакие привязки рекламного кабинета не являются задачей данного этапа.**
