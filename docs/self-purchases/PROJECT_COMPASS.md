## 1. Что строим

По сигналу или ежедневной проверке собственный SKU WB/Ozon → сбор собственных показателей и конкурентной среды → выявление причин → прозрачный расчёт сценариев и экономического эффекта → объяснимая рекомендация Hermes → решение человека → контроль фактического результата.

История самовыкупов — объект исследования причинной эффективности, **не предписанный способ продвижения**. Не создавать автоматизацию фиктивных заказов, платных/искусственных отзывов и обхода правил маркетплейсов.

## 2. Что сохраняем из первоисточника

- Разделение **новых товаров**, **проблемного рейтинга**, **прочих ситуаций**.
- Исторические пропорции «90/5/5» и «80/20» — только непроверенные оценки участников, а не готовые параметры кода.
- Текущий триггер «дни без продаж с учётом ценовой категории» — повод для проверки, не доказательство оптимального действия.
- Ключевой контекст — **реально сопоставимые конкуренты**: количество, отзывы, продажи, реклама, цена, ниша.
- Собственные продажи и экономика плюс **отдельно сохранённая экспертная оценка** продукта.
- Работа с низким рейтингом, где важно качество товара, важность для бизнеса и стоимость улучшений.
- Фактическое измерение органических продаж и прибыли после выбранных допустимых действий.
- Возможность решения **«ничего не делать / не увеличивать расходы»**.
- Обязательная фиксация неуверенности и ограничений источников.

## 3. Что не нужно выдумывать

Не считать известными:
- проверенные доли успешных случаев;
- исходную точную формулу и коэффициенты старого триггера;
- универсальный порог рейтинга (4–4,5 в разговоре — обсуждение, не утверждённый норматив);
- причинный эффект исторических самовыкупов;
- полноту/достоверность данных MPSTATS по отдельным конкурентам;
- наличие продакшн-инструментов изменения маркетплейса, их разрешений и фактов исполнения.

Каждый статус маркировать: **FACT** (подтверждённые данные), **MEETING_ESTIMATE** (оценка участников), **HYPOTHESIS**, **MODEL_ESTIMATE**, **APPROVED_DECISION**, **UNKNOWN**.

Проверять историю оценок/отзывов только при наличии действительно датированных данных провайдера. Не подменять их сегодняшним рейтингом. MPSTATS — аналитическая оценка рынка, не подтверждённые собственные оплаченные заказы.

Google workbook «_01_Продажи (новая)» и разработанный CSV-QA остаются **необязательными средствами последующей сверки**, а не блокером и не обязательной архитектурой первого пилота. Не развёртывать новые прямые WB/Ozon MCP специально ради первого исторического сравнения. Отдельно сравнивать продажи MPSTATS, рейтинг, отзывы, цены и аналоги; причинную эффективность не утверждать без контрольного сравнения. Сначала один завершённый кейс с 14-дневными сопоставимыми окнами, затем контроль.

## 15. Утверждено: точка отсчёта — появление отзыва, НЕ покупка

Источник: текущий `Реестр выкупов/отзывов`, поля `Дата выкупа`, `Дата отзыва`, `Ссылка на отзыв`; SQLite уже содержит `purchase_date`, `review_date`, `review_url`. Для исследования появления первых отзывов/изменения рейтинга и последующих заказов **T = review_date** (пока дата реестра не подтверждена как дата фактической видимой публикации). Без `review_date` исследование последствий отзыва не запускается. Периоды до/после считаются от T, покупки остаются отдельными историческими событиями. Учитываются новые датированные отзывы, рейтинг, заказы/продажи, наличие, цена, конкуренты; отсутствующие исторические данные — UNKNOWN. Исторический рейтинг MPSTATS нужно отдельно доказать. См. [REVIEW_PUBLICATION_EVENT_MODEL_20261022.md](REVIEW_PUBLICATION_EVENT_MODEL_20261022.md).
