### 2026-10-22 · MSP-SELF-D011 · Основное событие — дата отзыва, покупка лишь предшествует

- Статус: **APPROVED_DECISION** по прямому уточнению владельца, приоритетнее прежнего расчёта по `purchase_date` (MSP-SELF-D007, D008 и связанных опытов).
- При анализе последствий появления оценки или отзыва брать `review_date` из `Реестр выкупов/отзывов`, а не `purchase_date`. Только реально опубликованная дата, если она независимо подтверждена, получает `PUBLICATION_VERIFIED`; дата реестра = `REGISTRY_REPORTED_NOT_VERIFIED`.

- Две ветки: `first_reviews` (новая карточка, первоначальные отзывы) и `rating_recovery` (ранее сниженный рейтинг). После T наблюдать за **новыми датированными отзывами**, общим рейтингом, заказами и продажами; сравнивать с наличием, ценой, рекламой и конкурентами.
- Старые результаты `#512/#518` помечены `SUPERSEDED_PURCHASE_ANCHOR`: успешное чтение MPSTATS доказано, но анализ реакции на отзыв по ним недействителен. Установленная ранняя версия расчётного модуля должна быть заменена после безопасной приёмки.
- Канон: [REVIEW_PUBLICATION_EVENT_MODEL_20261022.md](REVIEW_PUBLICATION_EVENT_MODEL_20261022.md). Историческая стенограмма и первоначальная концепция остаются неизменными.

### 2026-10-23 · MSP-SELF-D022 · Обязательное наблюдение после каждой даты отзыва

- **Автор:** владелец. **Статус:** `APPROVED_DECISION`, немедленная поправка к действующему однократному анализу серии.
- **Триггер:** несколько выкупов/дат отзывов у одной карточки. Один отчёт «30 дней до первого и 30 дней после последнего» недостаточен: фиксировать последствия каждого последовательного записанного события, начиная с первого, затем второго, третьего и всех следующих.
- **Данные:** `self_purchase.quantity` из колонки **«Кол-во выкупов»** — повторяемый общий план по карточке; **«Дата отзыва» / `review_date`** — отдельное реестровое событие по завершённой строке, **не план**. `COUNT(completed rows)` не `SUM(quantity)`. Для одинаковой календарной даты несколько строк агрегируются в одну контрольную точку с явным числом строк.
- **Окна:** отдельно для каждого `review_date[k]`: `N` дней **до первой** даты и `N` дней **после текущей** даты, исключая день события. `N=min(30, завершённые дни после текущей даты до as_of, полные дни до следующего зарегистрированного отзыва)`. Следующий отзыв прерывает окно предыдущего, чтобы не смешивать этапы. Если дней нет — `POST_WINDOW_PENDING`; если `N<30` — `SHORTER_EQUAL_WINDOW_PRELIMINARY`. Общее сравнение после последнего оставить лишь дополнительным сводным итогом.
- **Доказательная оговорка:** записи отзывов не доказывают независимой публикации или пяти звёзд; данные MPSTATS являются оценками и должны запрашиваться за точные интервалы отдельно для каждой контрольной точки. До/после не доказывает причинный эффект. Никаких инструкций или механизмов реализации неаутентичных заказов/отзывов.
- **Реализация:** `series_analysis.py` → `checkpoints`; `series_report.py` → `build_series_checkpoint_reports`; семантический `self_purchase.yaml` v10; Skill Hermes и компас; тест `test_msp_self_review_checkpoints.py`. [Канон и датированный пример](PER_REVIEW_CHECKPOINT_WINDOWS_20261023.md).
- **Состояние установки:** GitHub-ветка и реальное содержимое `/home/hermes/.hermes/skills/productivity/msp-self-purchases` — разные артефакты. Действительную синхронизацию отмечать только по отдельному server read-back и checksum.
