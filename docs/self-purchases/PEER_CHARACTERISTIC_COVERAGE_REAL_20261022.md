## Источник, который можно проверить следующим (без смены исходной стратегии)

По официальной документации WB API метод `POST https://content-api.wildberries.ru/content/v2/get/cards/list` получает **собственные** карточки продавца. Хотя HTTP-метод `POST`, это запрос на получение информации, не создание карточек; он требует авторизованный токен соответствующей категории. Доступность именно нашего токена, его права, наличие нужных характеристик и разрешённость вызова на VPS пока **НЕ ПОДТВЕРЖДЕНЫ**.

Официальные источники:
- https://dev.wildberries.ru/knowledge-base/articles/019d50e0-4cd1-7756-809a-274ac5498b6d/pervyi-zapros-k-wb-api
- https://dev.wildberries.ru/en/docs/openapi/api-information

Это дополнительная опция для собственных товаров, **не обязательная замена MPSTATS** и не источник описаний чужих карточек. Не требовать от владельца новые токены до оценки имеющихся безопасных источников.

Следующий порядок проверки:
1. Проверить **существующие разрешённые** источники характеристик МСП/1С и статус read-only доступа через действующие механизмы интеграции. Рабочую базу 1С не менять; тестовая `NewBase` не доказывает актуальность живого каталога.
2. Если уже существует разрешённый, защищённый, read-only доступ к WB Content API, проверить одну собственную карточку без передачи токена в логи, GitHub или чат.
3. Для чужих товаров запросить доступные разрешённые подтверждённые данные отдельно; не подменять подробное описание предположениями из названия/изображения/цены.
4. Передать структурированные поля и метаданные источника в `peer_evidence.py`. Его статус `MATCHED_FIELDS_REVIEW_REQUIRED` **не является** окончательным подтверждением аналога.
5. При доказанной пригодности источников перейти к проверенной исторической группе, учёту дней наличия, рекламы, цены, экспертного качества товара и маржи; иначе явно `UNKNOWN`.

Действующие сервисы, расписания, реестры, Telegram и исходные исторические документы не изменять.
