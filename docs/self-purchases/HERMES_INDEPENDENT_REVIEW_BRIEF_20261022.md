## 1. Первоначальная идея — куда двигаться

### Почему появился проект

На совещании обсуждали два главных исторических применения самовыкупов: запуск новых карточек и попытки улучшить карточки с плохим рейтингом. Участники предварительно предположили структуру старых случаев: **90% новых товаров / 5% низких рейтингов / 5% прочих**; у новых товаров примерно **80%** ситуаций с одним инициированным 5-звёздочным отзывом и **20%** с другими пятизвёздочными отзывами. Это слова участников, **не проверенные выборкой**. Один вспоминаемый успешный случай восстановления рейтинга не позволяет оценить эффективность.

Значимая проблема: карточка может не продаваться из-за неверного продукта, цены, плохого содержания, отсутствия органического спроса, недостатка наличия, плохой видимости или давления конкурентов. История самовыкупов сама по себе не доказывает ни причину продаж, ни эффективность действий.

### Целевая роль Hermes

Создать **постоянного аналитика и прогнозиста собственных карточек WB/Ozon**, который:
1. Получает повод к анализу (например, новый товар, нет продаж N дней, падает рейтинг, слабый спрос, сигнал Telegram).
2. Восстанавливает **свои** ряды: фактические заказы, завершённые продажи/возвраты, доступность, цены и скидки, реклама, отзывы, история запланированных/выполненных событий и экономика.
3. Находит действительно сопоставимых **внешних** конкурентов: назначение, характеристики, комплектация, размер, ценовой сегмент и ниша; количество карточек, динамика продаж, цены, отзывы, рейтинги и присутствие в рекламе. Не сравнивает разные классы товаров.
4. Отдельно учитывает **экспертную оценку сотрудника** (качество/потенциал товара и нюансы производства) с указанием автора, даты и уверенности.
5. Исследует исторические кейсы, но не делает вывод о причинности по одному совпадению во времени.
6. Считает прозрачные метрики и экономически обоснованные сценарии, показывает неопределённость, предлагает **допустимые** действия или обоснованное «не предпринимать дополнительных расходов».
7. Получает подтверждение решения человека, фиксирует гипотезу, измеряет последующие фактические органические продажи и прибыль, сопоставляет с контролем и улучшает модель.

**Граница безопасности:** исторические самовыкупы и отзывы — данные для критического изучения; не проектировать и не запускать искусственные заказы, оплаченные фиктивные отзывы или способы обхода правил WB/Ozon. Полезные альтернативы: улучшение карточки/качества/наличия, законное продвижение, корректировка цены, проверка спроса, прекращение невыгодных вложений.

### Идея расчётов

Проверять эффективность не статическими «магическими» коэффициентами, а вычисляемыми величинами: скорость реальных продаж на дни наличия, продажи/возвраты по окнам, динамика цены к медиане **подобранных аналогов**, относительное количество отзывов с учётом выборки, доля рекламы и расходов, маржинальный вклад/ROI, прогноз прироста **органической** прибыли с доверительным диапазоном. Сначала определить на каких данных каждый показатель рассчитывается, затем калибровать/тестировать; отсутствие данных выдавать как `UNKNOWN`.

## 3. Архитектура проекта — что где находится

### На удалённом VPS REMOTE

- VPS Ubuntu 24.04, корень инфраструктуры `/opt/mcp/`.
- Работающий локальный checkout проекта: `/opt/mcp/projects/msp-server-stack/`; **его версия может отставать от GitHub main, и он может содержать чужие локальные изменения**. Не выполнять `git reset --hard`, `git pull` или глобальные миграции ради этой задачи.
- Основная рабочая БД: `/opt/mcp/data/msp/msp_data.sqlite3`.
- Скрипт импорта: `/opt/mcp/projects/msp-server-stack/apps/msp_data_sync/sync.py`.
- Обёртка ежедневной синхронизации и уведомлений: `apps/msp_data_sync/run_with_alerts.py`.
- Конфигурация: `config/msp-data/sync.json`; точные семантические правила: `config/msp-data/semantics/self_purchase.yaml`.
- Безопасные резервные копии: `/opt/mcp/backups/msp/`.
- Установленный Hermes Skill: `/home/hermes/.hermes/skills/productivity/msp-self-purchases/`.
- Отдельный MPSTATS Skill: `/home/hermes/.hermes/skills/productivity/mpstats/`. Отдельная система Telegram-сигналов имеет свой `msp-signals` Skill.

### Службы и задания

- `hermes-gateway.service` — существующий Hermes Gateway/Telegram, **НЕ служба самовыкупов**; не трогать.
- `hermes-dashboard.service` — интерфейс/локальный API Hermes на 127.0.0.1:9119, не путать с сервером MCP самовыкупов.
- `msp-data-sync.timer` — **user-systemd**, от пользователя `hermes`, календарь 08:00 Europe/Moscow ежедневно, `Persistent=true`.
- `msp-data-sync.service` — oneshot: обрабатывает четыре источника и отправляет изменение статуса в существующий Telegram (через `run_with_alerts.py`).
- `msp-signal-notify.service` — отдельный существующий контур сигналов, не новая служба для самовыкупов.
- GitHub self-hosted runner `msp-remote` — через **приватный** `msp-server-bridge` выполняются только заранее проверенные GitHub Actions jobs. Нельзя считать текст Issue произвольной shell-командой.
- На данном этапе **отдельных** `msp-self-purchase-analytics.service`, предиктивной модели, автоматического выполнения действий и полноценного самостоятельного MCP-сервера самовыкупов **ещё не создано**. Это новый функциональный контекст внутри имеющейся системы, а не новый работающий сервер.
