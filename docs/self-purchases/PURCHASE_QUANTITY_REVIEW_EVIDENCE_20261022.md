# МСП Самовыкупы — количество единиц и доказательства оценок (22.10.2026)

**Статус:** прямое дополнение владельца к семантике двух сценариев. Этот документ дополняет [правило даты отзыва](REVIEW_PUBLICATION_EVENT_MODEL_20261022.md), не отменяя его. Замороженные исходные стенограмма и концепция не изменяются.

## Что именно учитываем

В реестре «Реестр выкупов/отзывов» колонка **«Кол-во выкупов»** (F) уже передаётся в поле `self_purchase.quantity` SQLite. Для записи с `quantity = 3` это **три выкупленные единицы**, а не одна. В расчётах по новому товару и карточке с прежним низким рейтингом количество обязательно учитывать.

Рабочее допущение владельца: *одна выкупленная единица может соответствовать одной пятизвёздочной оценке*. Это именно допущение о возможном соответствии, **не установленный факт появления оценки**. Нельзя автоматически считать запись с `quantity=3` тремя опубликованными оценками по пять звёзд — таблица хранит лишь одну общую колонку «Дата отзыва» и одну «Ссылка на отзыв» для строки.

Не смешивать следующие величины:

| Показатель | Определение | Доказательство |
|---|---|---|
| `purchase_units` | `sum(quantity)` завершённых записей по карточке и выбранному периоду | Исходный реестр / SQLite |
| `registry_review_date` | Дата отзыва, указанная в реестре для строки | Подтверждена как запись в реестре, **не обязательно как день видимой публикации** |
| `verified_distinct_review_count` | Количество **уникальных** отзывов с проверенными датами, оценками и привязкой к конкретной записи/карточке | Реально полученные индивидуальные записи, если они доступны |
| `verified_five_star_review_count` | Количество уникальных проверенных опубликованных оценок со значением 5 | Только по фактически полученным оценкам, не из `quantity` |
| `unverified_potential_review_count` | Неподтверждённая часть гипотезы при наличии проверяемых связей | Не объявлять фактическими отзывами или источником роста рейтинга |
| `total_review_change`, `overall_rating_change` | Фактически зафиксированная динамика карточки до/после T | Нужны датированные исторические данные; не подменять текущим снимком MPSTATS |

**Оценки и заказы остаются разными сущностями.** Независимо не подтверждённый отзыв не равен нулю; он неизвестен. Нельзя считать все отзывы, не отмеченные как связанные с выкупом, «органическими», не имея независимых признаков происхождения.

## Два сценария

**Новый товар / первые отзывы:** фиксировать количество уже совершённых единиц по реестру, наличие подтверждённого опубликованного отзыва, динамику количества **других** датированных отзывов и оценочных продаж/заказов после появления отзыва. Отделять историю подозреваемых/связанных отзывов от остальных наблюдений; без доказательств не утверждать источник остальных отзывов. Даже если имеется одна запись `quantity=3` и дата отзыва, это ещё не три видимые оценки.

**Ранее слабый рейтинг:** фиксировать тот же `purchase_units`, проверенные оценки с их индивидуальными датами и исторический **общий рейтинг** карточки. Не строить величину рейтинга только из количества выкупов и заявленной пятизвёздочной гипотезы. Наблюдать, появились ли другие датированные отзывы, менялся ли общий рейтинг; учитывать наличие товара, цену, рекламу и похожие товары.

## Последовательность вычислений

1. Сопоставить `marketplace + store + marketplace_sku` с карточкой; взять завершённые покупки. Сложить `quantity` по действительно относящимся к исследованию строкам. Не считать число строк количеством единиц.
2. Взять `review_date` отдельно от `purchase_date`. Если даты отзыва нет, остановить **анализ последствий появления отзыва**, но оставить количество купленных единиц в учёте.
3. Если `quantity>1` и указана одна дата отзыва, признать **неизвестными** индивидуальные даты появления остальных возможных отзывов. При наличии отдельных достоверных публикаций учитывать каждую по собственному идентификатору/дате, без дублей.
4. Определить окна относительно **даты появления отзыва T**, а не даты покупки: `T−N … T−1`, `T+1 … T+N`, N по умолчанию 14; день T отдельно. Для нескольких **разных подтверждённых дат** публикации нельзя приписывать все последующие изменения первой дате — учитывать наложения и интервалы.
5. Получить через MPSTATS **доступную датированную историю** рейтинга, отзывов, оценочных продаж, цены и остатков, затем те же периоды сопоставимых конкурентов. Отсутствующие ряды отмечать `UNKNOWN`.
6. Выдать отчёт: `количество купленных единиц / сколько отдельных отзывов действительно подтверждено / сколько дат неизвестно / какие изменения наблюдались / возможные другие причины / уровень достоверности`. Не приписывать причинность и не формировать инструкции по искусственному созданию заказов или оценок.

## Технические слои

- **Google-источник:** не менять исходные F/G/H/I. Значение F — единицы, G — покупка, H — указанная дата отзыва, I — ссылка. Не считать одну ссылку набором `quantity` разных ссылок.
- **SQLite / импорт:** `self_purchase.quantity` уже хранит положительное целое. `completed` подтверждает покупку, не публикацию отзыва. Структуру исходной таблицы и расписание сервера менять не требуется.
- **Семантика:** `config/msp-data/semantics/self_purchase.yaml` — новый контракт `historical_unit_and_review_evidence`.
- **Логика:** `apps/msp_self_analytics/purchase_unit_audit.py` — чистый инструмент сводки купленных единиц и известных уникальных подтверждений; существующая `review_event.py` определяет статус даты отзыва, `retrospective.py` сравнивает периоды относительно отзыва.
- **Hermes:** перед заключением по обоим сценариям обязан учитывать число единиц, проверять статус дат и индивидуальных отзывов, а не подставлять планируемые оценки в фактический рейтинг.
- **Старые отчёты:** прежние сравнения только по количеству строк или от даты покупки остаются архивом и не используются для оценки эффекта опубликованного отзыва.

**Цель:** достоверный исторический разбор изменений карточки и независимых факторов; не моделирование количества искусственных оценок, необходимых для изменения рейтинга.
