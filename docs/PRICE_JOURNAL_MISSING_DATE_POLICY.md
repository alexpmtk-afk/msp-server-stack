# МСП — обязательное правило журнала изменения цен: нет даты → пропустить

**Решение владельца:** 22 октября 2026 г.  
**Статус:** APPROVED_DECISION, приоритет над устаревшими описаниями обработки пустой даты.  
**Применяется:** `price_journal_current` («журнал цен») и `price_journal_archive` («журнал цен (архив)»).

## Правило без исключений по другим полям строки

Если значение обязательной колонки **«дата»** пустое или содержит только пробельные символы, эта строка **не является событием изменения цены**. Пропустить её целиком **до** проверки SKU, маркетплейса, магазина, стоимости и других полей.

Для такой строки:
- **не создавать** `price_event`;
- **не добавлять** `sync_error` и `sync_run_issue`;
- **не увеличивать** `rejected`;
- **не переводить** источник в `partial` или `failed`;
- **не отправлять** Telegram/прочие уведомления о проблеме этой строки;
- **не ставить** задачу владельцу разбираться с этой строкой;
- считать её допустимым **игнорированием**, а не ошибкой качества данных.

Из соображений совместимости с действующей схемой SQLite количество таких проигнорированных строк учитывается существующим техническим счётчиком `skipped_technical`. Сам счётчик не является предупреждением и не отправляется владельцу. `source_rows` включает заполненные строки источника, включая пропущенные.

**Если дата присутствует, но некорректна** (например, невозможное 31.02.2026), это не «отсутствие даты», а настоящая ошибка в датированном событии. Аналогично при заполненной корректной дате ошибки SKU, магазина и числовых значений продолжают обычную проверку и уведомление. Не отключать контроль других ошибок.

**Уведомления:** когда источник цен после старого `partial` стал успешным, состояние старой ошибки снимается без отдельного сообщения «ВОССТАНОВЛЕНО». Это не отключает новые оповещения о действительно ошибочных датированных записях и не затрагивает сообщения об иных источниках.

## Обязательный приоритет для каждого агента

Это прямое окончательное указание владельца для данной категории строк. Любая прежняя документация, где отсутствие даты в журнале цен предлагается считать `rejected`/ошибкой или основанием для эскалации, **устарела**. Не возвращать данную тему в список проблем проекта, не просить владельца исправлять отсутствующую дату.

Не удалять прошлые записи ошибок и сообщения из исторических журналов: это исторические факты, но они не обозначают текущую проблему. Для живого статуса использовать самый свежий `sync_run`, результат тестов после установки и проверенную текущую версию парсера.

## Приёмка

На копии реальной SQLite и с проверенным источником:
1. Текущий и архивный журналы пропускают строки без даты, `rejected=0` при отсутствии иных ошибок.
2. Пустая дата в заполненной строке не создаёт ценовое событие и запись в `sync_run_issue`.
3. Повтор на той же версии источника идемпотентен и не посылает уведомлений.
4. Заполненная некорректная дата и другие реальные дефекты продолжают отклоняться.
5. Общее расписание 08:00 Europe/Moscow, Hermes Gateway и существующие остальные источники не меняются.
