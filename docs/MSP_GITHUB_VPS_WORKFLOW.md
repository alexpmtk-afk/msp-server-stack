# Совместная работа ChatGPT, Hermes и VPS

Статус: регламент одобрен владельцем 27.10.2026. Область: `alexpmtk-afk/msp-server-stack` и `alexpmtk-afk/msp-server-bridge`.

## Полномочия

В рамках порученной задачи Hermes разрешено читать оба репозитория, проводить аудит, исправлять код в отдельной рабочей копии, запускать тесты, создавать отдельные ветки, коммиты, публиковать их и открывать Pull Request. Это заменяет прежнее ограничение «изменения GitHub выполняет только ChatGPT».

**Отдельного согласования требуют:** прямые изменения `main`, слияние PR и установка изменений на VPS. Не включать auto-merge и не обходить согласование установки через Actions, bridge, расписания или фоновые процессы. Право исправлять исходники не разрешает операции с заказами, отзывами, ценами, рекламой, исходной базой или настройками маркетплейсов.

## Начало каждой задачи

1. Прочитать `AGENTS.md` и действующие инструкции проекта выбранной версии.
2. Получить актуальные remote refs. Записать репозиторий, базовую ветку и её commit SHA. Проверить открытые PR и чужую незавершённую работу.
3. Проверить локальный `git status`. Грязный рабочий или production-каталог не сбрасывать, не переключать и не обновлять через `git pull` ради синхронизации. Работать в отдельном checkout/worktree и собственной ветке.
4. Различать опубликованную feature-ветку, принятую версию и установленную версию. Код в открытом PR не обязан присутствовать в `main`; это не потеря изменений. Не использовать постоянный номер PR как вечный источник актуальности.

## Разработка и публикация

- Ветка содержит конкретную задачу. Не переписывать чужие ветки и не использовать force push для устранения расхождений.
- Перед исправлением сверить GitHub и фактически установленные модули/инструкции/семантику. Совпадение пути или импорт Python не доказывает выполнение кода.
- Выполнить необходимые проверки; для документации проверить diff и ссылки, для логики — подходящие тесты. Не объявлять CI успешным без чтения реального результата.
- Проверить отсутствие секретов и приватных данных. Архивы bridge, тексты отзывов, данные покупателей и сырые коммерческие ответы не переносить в публичный stack.
- Опубликовать свой коммит и открыть PR. Прочитать обратно remote SHA, базу, голову и состояние PR. Не сливать без отдельного согласования.
- Если ChatGPT изменил базу во время работы, разобрать конфликт содержательно в своей ветке; не затирать более новые решения целиком старым серверным файлом.

## Установка на VPS

Только после согласования конкретного результата:

1. Зафиксировать точный принятый commit SHA и перечень устанавливаемых файлов, включая Skill и необходимые справочники. `git pull` не является установщиком Skill.
2. Сделать резервную копию и записать контрольные суммы исходных файлов. Проверить наличие посторонних изменений и необходимые права.
3. Установить только согласованный набор; не изменять другие профили, сервисы и данные под видом обновления аналитики.
4. Сверить SHA-256 и выполнить настоящий запуск установленного обработчика. Изолированные тесты, реальный CLI, Gateway и Telegram end-to-end — отдельные уровни подтверждения.
5. Записать deployment manifest: репозиторий, исходный коммит, при наличии отдельная ветка-источник Skill, файлы/хеши, backup, проверки и оставшиеся ограничения. Не фиксировать токены в manifest.

Если согласованное срочное исправление возникло сначала на VPS, обязательно вернуть его в отдельный коммит/PR. Не оставлять единственную версию в активном Skill или переписке. Наличие deployment manifest не означает автоматической синхронизации: перед каждой работой нужна новая сверка.

## Итог задачи

Раздельно сообщать: что разработано локально; что опубликовано и в каком PR; какие проверки выполнены; что слито; что установлено на VPS; какой реальный запуск подтверждён. Если следующая операция требует согласования, показать конкретный PR/commit/план установки и указать, чего ждём. Секреты хранить защищённо вне репозитория. Авторизованный GitHub-доступ не доказывает доступ к VPS и не заменяет границы разрешения владельца.
