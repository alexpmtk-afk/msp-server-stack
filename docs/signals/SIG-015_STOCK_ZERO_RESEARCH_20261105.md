# SIG-015 — «Карточки с обнулёнными остатками»

**Исследование 05.11.2026. Бизнес-правило: частично согласовано. Автоизменения: НЕ РАЗРЕШЕНЫ.**

[Общий аудит двух сигналов](STOCK_SIGNALS_RESEARCH_20261105.md) · [источник ограничений](REVIEWED_RULES_2026-10-05.md)

## 1. Подтверждённый исходный сигнал

- Источник по сохранённому реестру: Google-таблица **`Обнуленные остатки`**, вкладка **`обнуленные остатки`**. Точный ID исходного файла не восстановлен; не подменять другой похожей таблицей.
- Проверка рассылки: `И(C2<>"";I2="")`; это **триггер** по готовым ячейкам, а не объяснение обнуления и не вся формула расчёта.
- Отправляемые исходной автоматизацией столбцы по архиву конфигурации: `A&B&C&E`. Их бизнес-названия ещё не извлечены из той самой таблицы.
- Расписание в исходном реестре: будни 08:00/12:00/16:00 по конфигурации оригинального процесса. Не путать с минутной периодичностью серверного notifier.
- Тип Telegram: «Карточки с обнулёнными остатками». `notify.py` умеет распознавать его и **только имитирует** «исключения проверены, остатки восстановлены», без API вызовов изменения.

## 2. Что действительно согласовано владельцем

**Только первый вариант обработки** (из утверждённых GitHub `REVIEWED_RULES_2026-10-05.md`):

1. Установить маркетплейс, компанию/кабинет, точный SKU и проверенную связь с внутренним артикулом.
2. Проверить, выполнялось ли для **этой же карточки/кабинета** действие SIG-016 по намеренному обнулению FBS; наличие другого сигнала само по себе не подтверждает выполнение.
3. Проверить связанное исключение в **программе Marketplace**. Точная структура и интерфейс этих исключений пока не описаны в доступных документах.
4. В этом первом сценарии как **возможное корректирующее действие** описано *удаление ошибочного исключения*. Это не удаление карточки маркетплейса и не удаление Telegram-сообщения. Условия, последствия и автоматическое восстановление остатков **ещё не утверждены**.

**Важно:** не выводить из этого правила, что каждое исключение надо удалять. Если обнуление является намеренным действием SIG-016 ради FBO, его нельзя автоматически отменять.

## 3. Что можно проверять на чтение

- В исходном уведомлении: ссылка/ID, время, точный marketplace, store, SKU, артикул; установить, в какой именно системе наблюдался ноль.
- Читатель `stocks_1c` через QRsite по `offer_id`, `blockid` и корректной дате; явный `quantity=0` отличать от `null` и отсутствия записи. Проверять свежесть среза и полноту загрузки.
- Независимый текущий опубликованный FBS/FBO остаток конкретной карточки/кабинета — только через **проверенный по инструментам и правам** источник; такого канонического метода в исследованных источниках ещё нет.
- Журнал действий/исключений программы Marketplace: нужны доказанные `SIG-016` изменения, а не текст тестового уведомления.
- Учётный склад 1С и продаваемый остаток FBS не равны автоматически. Резервирование, разные блоки и отсутствие строки остаются открытыми вопросами, а не поводом подставлять ноль.

## 4. Проект будущих диагностических веток — НЕ согласованный алгоритм

| Наблюдение | Предварительная трактовка | Пока допустимо |
| --- | --- | --- |
| Достоверный ноль в 1С и на маркетплейсе | Возможно реальное отсутствие товара | Сообщить, без «восстановлено» |
| Положительный остаток 1С, но FBS ноль | Возможны намеренное обнуление, исключение, сбой синхронизации или другая причина | Определить причину, не восстанавливать автоматически |
| Подтверждённое действующее обнуление SIG-016 в том же кабинете | Возможно осознанная распродажа FBO | Не отменять без нового решения |
| Доказанное ошибочное исключение Marketplace | Кандидат на удаление исключения по первому согласованному сценарию | Предложить решение владельцу; исполнение только после утверждения контракта |
| Недоступные/устаревшие/расходящиеся источники | Неопределённость | `УТОЧНИТЬ`, не принимать ноль и не править |

Эта таблица — **гипотезы классификации для обсуждения**, а не разрешённый автомат принятия решений.

## 5. Открытые пункты к совместному согласованию

1. Семантика столбцов C/I и upstream формул **именно оригинальной** вкладки; что такое состояние «обнулены» (FBS, FBO, все карточки/кабинеты, блокировки)?
2. Как достоверно читать **факт исключения Marketplace** (не путать с Telegram) и статус его применения? Ключ, тип, версия, эффект, владелец, права.
3. Какие причины нуля считаются нормальными и какие требуют вмешательства? Граница между SIG-015 и SIG-016.
4. При каких условиях снятие исключения безопасно и как подтвердить итог без ложного восстановления остатков?
5. Нужно ли подтверждение человеком, какие кнопки/текст и кому направлять? **Не заимствовать** модель SIG-032 без нового решения.
6. С какой частотой проверять исходные данные и через какой период считать задачу решённой? Как исключить споры с параллельными механизмами.
7. Нужен ли адресный API/MCP инструмент и readback действительного FBS/исключения. Ни один метод записи по этому назначению не подтверждён.
