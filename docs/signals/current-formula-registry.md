# Текущий реестр сохранённых формул сигналов

## Назначение

Этот файл фиксирует фактический реестр сохранённых формул, по которым в текущей системе формируются и отправляются сигналы.

Это **исходный материал для миграции**, а не готовое техническое задание серверной реализации.

Ключевой принцип:

```text
формула в реестре ≠ обязательно полная бизнес-логика сигнала
```

Часть формул только проверяет, заполнена ли уже рассчитанная ячейка в Google-таблице. В таких случаях перед переносом на сервер нужно отдельно найти и описать upstream-расчёт, который формирует значение этой ячейки.

В публичную документацию намеренно не переносятся Telegram-ники ответственных, приватные ссылки на сообщения и сведения о редакторах: для архитектуры сигнала они не нужны.

## Предварительное разделение

### Прямые кандидаты для направления Marketplace-сигналов

Сюда относятся сигналы по остаткам, ценам, карточкам, FBO/FBS, рекламе, заказам/передаче товаров и отсутствующим данным Marketplace.

Это **не означает**, что для них уже определены MCP-инструменты. Реестр лишь подтверждает, что такие сигналы фактически существуют в текущем процессе.

### Смежные процессы

В текущем реестре также присутствуют сигналы по:

- ГЗП и срокам производства;
- расчёту себестоимости новых товаров;
- задачам по новым товарам;
- отзывам и чек-листам;
- самовыкупам.

Их не нужно автоматически превращать в отдельные MCP-сигналы в рамках этого раздела. Решение о включении принимается отдельно при фактической проработке.

### Тестовые записи

Тестовые копии и служебные проверки сохраняются в реестре как свидетельство текущей системы, но не считаются самостоятельными бизнес-сигналами для новой архитектуры.

## Что нужно выяснять для каждого сигнала при миграции

Для каждого выбранного сигнала отдельно устанавливается:

1. Что именно рассчитывается в исходной Google-таблице до проверки сохранённой формулы.
2. Какие исходные данные нужны для расчёта.
3. Есть ли эти данные в базе Marketplace Андрея и доступны ли они через API.
4. Является ли сохранённая формула полной бизнес-логикой или только проверкой готового значения.
5. Какой структурированный объект сигнала должен получить серверный обработчик.
6. Какое действие допустимо после сигнала.
7. Нужен ли MCP/API-инструмент и какой именно.
8. Требуется ли подтверждение человека.
9. Как проверяется фактический результат действия.
