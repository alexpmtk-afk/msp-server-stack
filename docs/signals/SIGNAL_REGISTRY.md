# Единый реестр шести сигналов МСП

Владелец поручил создать 29.10.2026. Это пассивный аудит, не новый исполнитель.

## Расположение и команды

SQL: `/opt/mcp/data/msp/msp_signal_registry.sqlite3`.
Код: `/home/hermes/.local/share/msp/signal-registry/registry.py`.
Состояние: `python3 /home/hermes/.local/share/msp/signal-registry/registry.py status`.
Последние записи: та же команда с `list --limit 30` вместо `status`.
Карточка, товары, обратная связь, действия и все события: `show --id ID`.
Фоновая сверка существующих архивов/журналов каждые 10 секунд:
`msp-signal-registry.service` (user systemd). Новые Telegram updates принимает
пассивный `msp-signal-registry` внутри уже существующего Gateway, группа -20000,
до обработчиков, способных остановить дальнейшую маршрутизацию.
Нет getUpdates, новых ботов, сетевых API-запросов, сообщений и действий на МП.
Приёмник не перезапускает Gateway. `gateway_ready.json` доказывает подключение
к процессу; `last_ingress.json` — наблюдение update, но не всю живую приёмку.

## Смысл данных

- Шесть типов: SIG-002, SIG-015, SIG-016, SIG-021, SIG-022, SIG-032.
- `signals`: исходное сообщение, тип, исходная дата поступления UTC, время
  первого/последнего чтения, ссылка, текст, признак исторической загрузки,
  `extra_json` для будущих полей. Несколько товаров живут в `subjects`.
- `subjects`: точные SKU/внутренние артикулы; связь по `product_listing`
  сохраняет маркетплейс и магазин. Не выдумывать соответствия.
- `feedback`: **отработка = получена обратная связь**, включая Нет и emoji-reply.
  Это НЕ означает разрешение любому участнику менять цены и НЕ доказывает успех.
  Дата/автор/чат/сообщение/текст/способ связи сохраняются отдельно.
- Область: Сигналы МП; Удалённый сервер, тема 758; Hermes Group; ЛС владельца.
  В теме/ЛС обратная связь владельца, в Group — участников. Чужие каналы,
  реакции (не сообщения), и кнопки других проектов не учитываются.
- Reply к известной карточке — точная привязка. Без reply нужен точный артикул
  или SKU и подходящий тип. Несколько сигналов того же товара — `ambiguous`,
  без автоматического назначения и закрытия. Имена товаров приблизительно
  не сопоставлять. Не привязывать ответ к сигналу, пришедшему позже ответа.
- `actions`: отдельные площадка, кабинет, товар, job/command, статус, причина,
  время действия (если известно), время наблюдения и исходное подтверждение.
  `updated` ≠ `already_equal` ≠ `pending` ≠ `failed` ≠ `unknown` ≠ `simulation`.
  `execution_done` Orgobot НЕ подтверждает действительное изменение цены.
  Доказательства прежнего ценового журнала доступны в `events`.
- `events`: неизменяемые события и снимки источников, а не перезаписываемая
  история. В `actions` — последний полученный результат каждой операции.
- `v_signal_registry`: удобная сводка, первая/последняя обратная связь,
  отдельные сводки отработки и исполнения. `confirmed_results_available`
  означает наличие подтверждённых карточек, НЕ доказанную полноту всей области.
- Все сохранённые времена UTC с offset; для календарных отчётов отображать
  Europe/Moscow. Старое неизвестное время = NULL. Внешние времена без часового
  пояса сохраняются в исходном JSON, не выдаются за проверенное время UTC.
- Архив покрывает только полученное существующим ботом. Историческая загрузка
  НЕ полная история Telegram, не повторяет отправки и команды. Прямые команды
  без единственного соответствующего сигнала остаются отдельными событиями/
  непривязанными действиями и не закрывают произвольный сигнал.

## Работа агента и дополнение данных

Перед анализом отработки читать `status`, затем нужный `show`. При отказах
источников `health.error` не считать журнал полным. Для SQL открывать `mode=ro`.
Неизвестный исход явно так и писать; действие пользователя не равно исполнению.

Если контекст переписки позволяет точно разобрать `ambiguous`, связать
сохранённое сообщение: `link --id SIGNAL_ID --chat CHAT_ID --message MESSAGE_ID`.
Команда требует существующее сообщение и сигнал, сохраняет событие ручной
привязки. Не снимать неоднозначность догадкой. Сообщение без артикула и reply
можно связать этой командой после подтверждения контекста.

При ручном выполнении/анализе, для которого пока нет журнала исполнителя,
записать результат отдельной CLI-командой:
`record-action --id ID --key UNIQUE_OPERATION_KEY --offer ARTICLE --marketplace wb --cabinet NAME --status failed --detail 'конкретная причина' --evidence 'источник/квитанция' --at ISO8601`.
`--at` можно опустить при неизвестном времени; для updated/already_equal
обязательно подтверждение `--evidence`. Эта команда записывает только факт,
НЕ запускает действие. Для четырёх прежних имитаций использовать simulation,
пока отдельно не разрешён реальный исполнитель.

## Проверка/восстановление

`python3 /home/hermes/.local/share/msp/signal-registry/test_registry.py -v`.
Тесты используют изолированные SQLite в Hermes scratch и не используют сеть.
`sync` сверяет существующие источники только чтением, идемпотентен. Потерянные
во время остановки Gateway сообщения Bot API не гарантирует восстановить.
Не заменять живую приёмку фикстурой или отправкой от имени владельца.

Перед обновлением резервировать текущий код/manifest и SQLite через backup API;
не менять соседние notify/data-sync/ценовые/размерные обработчики. Откат:
выключить ТОЛЬКО msp-signal-registry.service и его plugin, сохранить SQLite.
Смена схемы — совместимая миграция с новой версией, данные не удалять.

## Обязательное ведение с 29.10.2026 — поручение владельца

Ответственный за ведение — Hermes. Реестр един для всех чатов, агентов и
исполнителей на этом сервере; смена сессии не отменяет обязательства.
Каждый поступивший и считанный сигнал SIG-002/015/016/021/022/032,
обратная связь и каждое предпринятое действие должны сохраняться здесь.
Отсутствие ответа также видно: сигнал остаётся ожидающим, а не исчезает.

- Автоматический приём работает в существующем Telegram Gateway; фоновая
  сверка подключённых архивов и журналов — каждые 10 секунд независимо от чата.
- Перед работой агент читает status/show; после работы проверяет show и
  наличие обратной связи и результатов по всей затронутой области.
- Ручные и новые исполнители обязаны записывать непокрытые результаты через
  record-action, а обратную связь связывать через link по доказанному контексту.
  Стабильный ключ операции сохранять при повторном чтении; не создавать дубли.
- В результат включать конкретное действие, товар, площадку, кабинет, время,
  статус, причину отказа/частичного результата и подтверждение. Отказ владельца,
  ожидание и отсутствие подтверждения не выдаются за выполненное изменение.
- Если сохранение не удалось, отработка не считается полностью оформленной:
  сохранить доступную квитанцию, сообщить о пробеле и восстановить запись после
  сверки. Не повторять действие на маркетплейсе ради записи в журнал.
- Новый автоматический маршрут не считать интегрированным, пока его реальные
  записи не читаются в этом реестре. Произвольные действия стороннего агента
  без журнала автоматически не наблюдаются; интеграция обязательна.
- При передаче другому агенту передавать ID сигнала/операции, а не создавать
  новый реестр. Историю не обнулять. Дополнительные поля — совместимой миграцией.

Специальный навык: `/home/hermes/.hermes/skills/productivity/msp-signal-registry/SKILL.md`.
Серверная семантика: `config/msp-data/semantics/signal_registry.yaml`.

## Исходники и проверка перед установкой

Исходники: `apps/msp_signal_registry/registry.py`, `test_registry.py` и
`plugin/`; unit: `systemd/user/msp-signal-registry.service`.
Из чистого checkout выполнить `python3 apps/msp_signal_registry/test_registry.py -v`.
В окружении установленного Hermes с python-telegram-bot выполнить отдельно
`python apps/msp_signal_registry/plugin/test_plugin_isolation.py -v`.
Последний тест берёт ТОЛЬКО соседний кандидат registry.py, перенаправляет
базу/квитанции в изолированную папку и не подключается к живому Gateway.
Ожидаются 15 тестов реестра и 1 тест плагина, не включая резервные копии.

Установка по поручению владельца: сохранить предыдущие файлы и online SQLite
backup, скопировать registry.py/test_registry.py/этот документ в каталог кода,
plugin/__init__.py и plugin.yaml — в ~/.hermes/plugins/msp-signal-registry,
unit — в ~/.config/systemd/user. Проверить SHA-256 всех файлов и тесты, затем
`systemctl --user daemon-reload` и `systemctl --user enable --now msp-signal-registry.service`.
Включить ТОЛЬКО этот плагин: `hermes plugins enable msp-signal-registry --no-allow-tool-override`.
При обновлении фабрика wire имеет новую версию; удалить прежний observer из
группы -20000 до подключения нового. Проверять gateway_ready.json: один observer,
ожидаемая версия/хеш и существующий PID. CLI acknowledgement не заменяет квитанцию.
Не перезапускать Gateway, notify, ежедневный data-sync или исполнителей МП.

Изменение кода и инструкции в GitHub не означает установки. Факт текущей
установки и точные хеши — в серверном `manifest.json` рядом с registry.py.
Код реестра не предоставляет удалённый API чтения базы сам по себе; агент без
доступа к терминалу должен использовать имеющийся разрешённый канал сервера.
