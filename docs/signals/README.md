# Карта сигналов Marketplace

## Действующая семантика Hermes (09.10.2026)

Для ручных запросов агенту Hermes («обработай сигналы», «Поднять цену», Сигналы МП) используется Skill `msp-signals` из `apps/hermes/msp_signals_skill/SKILL.md`, установленный на REMOTE в `/home/hermes/.hermes/skills/productivity/msp-signals/`. Установка: `scripts/deploy/install-msp-signals-skill.sh`. Канонические правила шести сигналов: `REVIEWED_RULES_2026-10-05.md`. Фоновый обработчик: `apps/msp_signal_notify/notify.py` (проверка раз в 60 секунд, только тестовые сообщения).

Ключевое правило `SIG-002`: когда известен остаток `_N` дней, но нет даты поступления с производства, это означает, что товар не заказан на производство. **Рекомендовать поднять цену**, а не заявлять о невозможности решения из-за отсутствующей даты. Реальных действий с ценами нет. Если дата указана некорректно, это отдельная ветка «недостаточно данных».

**Различать:** установленный Skill для *ручного анализа* и отдельный автоматический notifier для *тестовых уведомлений*. Одно не заменяет другое. Устаревший ниже раздел «Текущий предполагаемый входной контур» является историческим проектированием, а не описанием уже развёрнутого Telegram-архива.

Этот раздел описывает бизнес-логику сигналов Marketplace для проекта `msp-server-stack`.

Целевая цепочка обработки:

```text
данные → условие → сигнал → решение → инструмент → действие → проверка результата
```

## Архитектурный принцип

Обработка сигнала разделяется на три уровня:

1. **Расчёт сигнала** — обычный программный код получает данные и проверяет формальное условие.
2. **Решение** — агент получает структурированный сигнал, при необходимости запрашивает дополнительные данные и определяет рекомендуемое действие.
3. **Исполнение** — действие выполняется только через заранее реализованный и безопасный API/MCP-инструмент.

Агент определяет **что** нужно сделать. Исполнительный инструмент определяет **как** это сделать технически.

Google-таблицы могут использоваться для просмотра и аналитики, но в целевой архитектуре не должны быть обязательным техническим звеном обработки сигнала.

Перед созданием нового источника данных сначала проверяется, есть ли нужные данные в существующей базе Marketplace Андрея и можно ли получить их через API.

## Текущий предполагаемый входной контур

На первом этапе источником готового сигнала может быть специальный Telegram-канал сигналов. Рабочее название канала — **Signal**, точное название пока не определено.

Предварительная логическая цепочка:

```text
Telegram-канал сигналов
→ Telegram-бот на REMOTE
→ серверный контур обработки
→ определение типа проблемы и требуемого действия
→ подходящий MCP/API-инструмент
→ API Marketplace
→ проверка фактического результата
→ отчёт
```

Telegram в этой схеме является источником сообщения о проблеме, а не местом хранения бизнес-логики или исполнения действия.

MCP рассматривается прежде всего как контролируемый исполнительный слой: для каждого поддерживаемого действия должен существовать отдельный безопасный инструмент. Серверный контур обработки должен определить, какое действие требуется, и вызвать соответствующий инструмент. Точная техническая реализация маршрутизации пока не определена.

В дальнейшем источник сигнала может измениться без изменения общей исполнительной схемы. Например, вместо готового Telegram-сообщения сигнал сможет формироваться напрямую серверным расчётным модулем на основании базы Marketplace.

## Что пока не определено

На текущем этапе специально **не фиксируются как решённые**:

- точное название Telegram-канала сигналов;
- точный маршрут сообщения внутри REMOTE;
- какой компонент будет распознавать тип сигнала и выбирать инструмент;
- архитектура будущего MCP-сервера;
- окончательные названия MCP/API-инструментов;
- контракты этих инструментов;
- правила автоматического или ручного подтверждения действий;
- конкретные бизнес-правила для отдельных типов сигналов, пока они не протестированы и не подтверждены.

Эти элементы уточняются по мере фактической проработки и тестирования каждого типа сигнала.

## Исходный реестр текущей системы

Фактические сохранённые формулы текущих сигналов зафиксированы отдельно: [текущий реестр формул](current-formula-registry.md).

Важно: сохранённая формула может быть только последней проверкой уже рассчитанной ячейки. Поэтому перед переносом каждого сигнала на сервер нужно отдельно найти исходный расчёт в таблице и определить реальные входные данные.

## Правила ведения карты

- Не придумывать бизнес-правила, которых ещё нет.
- Неопределённые параметры фиксировать в разделе **«Открытые вопросы»** конкретного сигнала.
- Не создавать отдельный файл сигнала до начала его фактической проработки.
- Формула обнаружения сигнала не обязана находиться внутри MCP.
- MCP/API используется как контролируемый набор инструментов для получения данных и исполнения действий.
- Успешная обработка сигнала должна заканчиваться проверкой фактического результата действия.

## Статусы

- **идея** — сигнал известен, логика ещё не описана;
- **логика описана** — условие и предполагаемый процесс зафиксированы;
- **данные подтверждены** — источники и поля данных проверены;
- **API отсутствует** — для исполнения нет готового инструмента;
- **готов к разработке** — логика, данные и контракт действия определены;
- **реализован** — программная реализация создана;
- **протестирован** — полный цикл сигнала проверен на фактических данных.
