# Карта сигналов Marketplace

Этот раздел описывает бизнес-логику сигналов Marketplace для проекта `msp-server-stack`.

Целевая цепочка обработки:

```text
данные → условие → сигнал → решение → инструмент → действие → проверка результата
```

## Архитектурный принцип

Обработка сигнала разделяется на три уровня:

1. **Расчёт сигнала** — обычный программный код получает данные и проверяет формальное условие.
2. **Решение** — агент получает структурированный сигнал, при необходимости запрашивает дополнительные данные и определяет рекомендуемое действие.
3. **Исполнение** — действие выполняется только через заранее реализованный и безопасный API/MCP-инструмент.

Агент определяет **что** нужно сделать. Исполнительный инструмент определяет **как** это сделать технически.

Google-таблицы могут использоваться для просмотра и аналитики, но в целевой архитектуре не должны быть обязательным техническим звеном обработки сигнала.

Перед созданием нового источника данных сначала проверяется, есть ли нужные данные в существующей базе Marketplace Андрея и можно ли получить их через API.

## Карта сигналов

| Сигнал | Источник данных | Условие срабатывания | Что проверить | Рекомендуемое действие | Инструмент API/MCP | Нужен человек | Статус |
|---|---|---|---|---|---|---|---|
| Нехватка остатка до следующего поступления / повышение цены | Остатки + динамика заказов/продаж + дата следующего поступления; источник — база Marketplace Андрея/API, точка доступа уточняется | Прогнозируемая дата окончания товара раньше даты следующего поступления | Корректность остатка, динамику продаж, дату поступления и дополнительные ограничения решения | Рассмотреть повышение цены для снижения темпа продаж | Предполагаемый `change_price`; наличие и контракт нужно подтвердить | Пока не определено | Проектирование |

## Правила ведения карты

- Не придумывать бизнес-правила, которых ещё нет.
- Неопределённые параметры фиксировать в разделе **«Открытые вопросы»** конкретного сигнала.
- Не создавать отдельный файл сигнала до начала его фактической проработки.
- Формула обнаружения сигнала не обязана находиться внутри MCP.
- MCP/API используется как контролируемый набор инструментов для получения данных и исполнения действий.
- Успешная обработка сигнала должна заканчиваться проверкой фактического результата действия.

## Статусы

- **идея** — сигнал известен, логика ещё не описана;
- **логика описана** — условие и предполагаемый процесс зафиксированы;
- **данные подтверждены** — источники и поля данных проверены;
- **API отсутствует** — для исполнения нет готового инструмента;
- **готов к разработке** — логика, данные и контракт действия определены;
- **реализован** — программная реализация создана;
- **протестирован** — полный цикл сигнала проверен на фактических данных.
