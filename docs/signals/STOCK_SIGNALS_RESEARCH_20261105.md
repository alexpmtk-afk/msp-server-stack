## Не смешивать три разных типа остатка

1. **Остаток 1С:** QRsite `stocks_1c` / REST `GET /api/v1/stocks/1c/` по `offer_id`, `blockid`, дате. Это источник факта учётного склада, **не автоматическое доказательство доступного остатка FBS конкретного кабинета**. `quantity=0` — настоящий ноль, `null` — неизвестно, отсутствие строки — не ноль.
2. **FBS на маркетплейсе:** опубликованное/продаваемое количество в конкретном магазине, складе, SKU; метод чтения и адресной записи **ещё не подтверждены** для SIG-015/016. Значение FBS не выводить напрямую из 1С без контракта синхронизации.
3. **FBO на маркетплейсе:** независимый запас на стороне маркетплейса; не обнулять при SIG-016 и не прибавлять к FBS для проверки восстановления.

Упорядоченный ключ цели: `marketplace + store/company + marketplace_sku` → проверенный внутренний `offer_id/internal_article`. Не выбирать товар по одному текстовому названию. Точная идентификация склада FBS и блока 1С требует отдельного согласованного соответствия.

## Связь двух процессов — только после доказательства

`SIG-016` может объяснять намеренное обнуление FBS, которое позднее выявит `SIG-015`. Но `SIG-015` не обязательно является следствием `SIG-016`; возможны и другие причины, которые пока не классифицированы. Проверять совпадение **всего ключа цели**, времени и подтверждённого события изменения. Одно соседнее сообщение в Telegram не доказательство причинной связи.

**Запрещённый вывод:** «в 1С есть остаток, а карточка обнулена → всегда снять исключение/вернуть FBS». Это может отменить намеренное решение для распродажи FBO.

## Доступные механизмы и ограничение

- QRsite `stocks_1c`, `stock_1c_history`, `marketplaces_blocks` — документированные read-only инструменты; см. [ANDREY_QRSITE.md](../ANDREY_QRSITE.md). Состояние разрешений и фактический tool list перепроверять при начале реализации.
- В проверке QRsite от 04.10.2026 **не было подтверждённых методов управления FBS/исключениями Marketplace**. Наличие `marketplaces_dimensions_update` для другого SIG-032 не является инструментом изменения остатков.
- Пассивный `msp-signal-notify.service` регистрирует шесть сигналов, помечает сообщения как имитации; не является исполнителем FBS.
- Отдельный подготовленный [реестр событий сигналов, PR #94](https://github.com/alexpmtk-afk/msp-server-stack/pull/94), на момент проверки 05.11 **открыт и не merged**; в описании заявлена локальная установка пассивного observer, но реальный E2E по новым сигналам не подтверждён. Не путать реестр событий с бизнес-решением или действующим изменением FBS.
- [Общий реестр статуса, draft PR #121](https://github.com/alexpmtk-afk/msp-server-stack/pull/121) — будущая единая точка прогресса, в `main` на момент проверки отсутствует. При принятии этого досье включить туда ссылки и четыре статуса: `CODE / MERGED / DEPLOYED / LIVE_E2E`.

## Что подтверждено и что предстоит

**Подтверждено из источников:** названия, разные вкладки и условия отправки, тестовая работа notifier, базовые правила SIG-015/016, чтение 1С через QRsite, отсутствие согласованной безопасной записи.

**Не подтверждено:** фактическая семантика C/I и E1, upstream формулы оригинальных вкладок, все причины нулевого остатка, соответствие FBS-склада 1С, адресный write API и проверка статуса исключения Marketplace, правило автоматического восстановления, подтверждение пользователя, реальные примеры с полным исходным payload.

**Следующий совместный этап:** согласовать два раздельных дерева решений на примерах настоящих сигналов и исходных данных, затем уже поручить Hermes реализацию Skill/Gateway/исполнителей и тесты. Пока — **только исследование и фиксация**, без выполнения внешних действий.
