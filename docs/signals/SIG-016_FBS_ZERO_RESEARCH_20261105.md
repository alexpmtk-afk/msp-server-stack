# SIG-016 — «Нужно обнулить FBS для распродажи FBO»

**Исследование 05.11.2026. Бизнес-назначение согласовано; исполнитель и условия записи — НЕТ.**

[Общий аудит двух сигналов](STOCK_SIGNALS_RESEARCH_20261105.md) · [утверждённые ограничения](REVIEWED_RULES_2026-10-05.md)

## 1. Подтверждённый исходный сигнал

- Источник в исходном реестре: Google-таблица **`Обнуленные остатки`**, вкладка **`обнулить ФБС распродажа ФБО`**.
- Условие отправки: `И(E1>0;E1<>"остаток ФБС 2")`. Без содержимого оригинальной вкладки нельзя утверждать, что `E1` — остаток на маркетплейсе или число товаров. Сравнение с текстом `остаток ФБС 2` — часть **существующего триггера** и должно исследоваться в контексте source-формулы.
- Передаваемые при исходной рассылке столбцы по архиву: `A&B&D`, значения их заголовков ещё не подтверждены.
- Расписание исходной рассылки: будни в 09:00 и 16:00.
- Серверный пассивный обработчик распознаёт заголовок SIG-016 и отправляет отчёт с пометкой **«ИМИТАЦИЯ: FBS обнулён»**. Это не запись данных. Не считать уведомление доказательством изменения.

## 2. Утверждённая бизнес-цель и границы

**Когда приоритетно распродать накопленный FBO, отключить именно продажу по FBS** для указанного товара/кабинета/маркетплейса.

Правила, подтверждённые в `REVIEWED_RULES_2026-10-05.md`:

- обнулять **только FBS**, а **не FBO**;
- не распространять операцию на другие товары, юридические лица, магазины и маркетплейсы;
- внутренний артикул сохранять без преобразования и домыслов;
- реальное изменение не выполнять до наличия проверенного адресного API/MCP, проверки результата и защиты от повторов.

**Не утверждено:** порог FBO, минимальный остаток FBS, длительность блокировки, критерий окончания распродажи, автоматический возврат FBS, размер исключения, кто подтверждает и обязан ли подтверждать. Из `E1>0` это **не выводится**.

## Актуальное описание MCP возможностей для SIG-016 (05.11.2026)

В предоставленном владельцем тексте QRsite MCP прямо приведен сценарий для Ozon: обнулить FBS конкретного товара на основном FBS-складе и добавить товар в **постоянные исключения** для распродажи FBO. Также описаны ручная установка количества на складе, настройка исключения, история операций и проверка, принят ли запрос и совпадает ли текущий остаток с заданным.

**Функциональность описана, но конкретные имена MCP-методов, сигнатуры, права Hermes, последовательность «ноль + исключение», атомарность и live E2E ещё НЕ проверены.** Для WB есть отдельный пример установки ручного остатка и исключения; точное тождество процесса Ozon пока не доказано.

Проект будущей обработки без исполнения: идентифицировать marketplace/кабинет/SKU/FBS-склад; прочитать FBS, FBO и активное исключение; проверить, не обнулено ли уже; выяснить бизнес-основание/длительность; только после согласования вызвать документированный адресный инструмент; прочитать итог, историю и статус синхронизации; исключить гонку с SIG-015. **Автоматическая запись до согласования запрещена.**

Первичный раздел: https://qrbott.ru/api/v1/mcp/docs/#mcp-marketplace-stocks . Полная спецификация API не прочитана.

## 3. Подготовка перед любым будущим действием

1. Однозначно сопоставить `marketplace + store/account + marketplace_sku` и внутренний `offer_id`. При нескольких SKU/складах не применять массовое действие без доказанного охвата.
2. Отдельно получить текущий FBS-остаток целевого кабинета/склада, актуальный FBO-остаток и дату/время измерений. Читатель QRsite `stocks_1c` показывает **учётный запас 1С** и не подменяет опубликованные FBS-остатки.
3. Проверить действующее **исключение Marketplace**, его назначение и конфликт с SIG-015. Нельзя трактовать нулевой FBS, уже установленный вручную, как требование повторного обнуления.
4. До реализации проверить по точному инструменту, способен ли API адресно менять **только выбранный** маркетплейс, магазин, FBS-склад и карточку. Если инструмент массовый или область недостаточно ясна — **запретить вызов**, не «сначала изменить всем, потом восстановить».
5. После отдельного решения владельца определить подтверждение, `request_key`/идемпотентность, чтение результата, способ ручной отмены и аварийные сценарии. Это **требования к будущему проектированию**, не уже установленные функции.

## 4. Проект дерева решений — НЕ согласованный алгоритм

| Диагностический факт | Предложение |
| --- | --- |
| Исходный сигнал есть, но товар/кабинет неоднозначны | `УТОЧНИТЬ`; не менять ничего |
| Целевая карточка уже имеет проверенный FBS=0 | `УЖЕ НОЛЬ`; не отправлять повторную запись |
| FBO или FBS неизвестны, срез устарел | `УТОЧНИТЬ`; не использовать данные другого склада |
| Подтверждённое желание сохранить FBO и сделать FBS=0 в точной области, есть проверенный адресный инструмент | Кандидат на согласованное действие с однократной записью и readback |
| Одновременно открытый SIG-015 по той же карточке | Проверить пересечение намерений; не запускать конкурирующие процессы восстановления/обнуления |

**Внимание:** ни один из предложенных переходов не означает разрешения выполнять запись.
