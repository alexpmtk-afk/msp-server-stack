## R1 — неполный preflight зависимостей Ozon (обязательная доработка B5)

Файл `apps/msp_marketplace_reports/archive.py:230–255`, `_rebuild_ozon_annual`.

Новая `_verify_previous` вызвана для обновляемого месяца и старого годового файла. Остальные месяцы по-прежнему проверяются отдельной старой логикой: только SHA/status/count. Поля schema/dataset/cabinet/period/bytes не сверяются с ожидаемыми значениями.

Точное искусственное воспроизведение:

1. Импортировать Ozon FINAL `2026-01`, создать штатные месяц/year.
2. Только в manifest январского файла заменить `schema: 1` на `schema: 2` (CSV и его SHA остаются прежними).
3. Импортировать `2026-02`.
4. Результат: исключения нет; annual_changed=True, verify=True. Документ с несовместимой схемой использован для публикации нового проверенного годового файла.

Повторено с неправильными dataset/cabinet/period/bytes января: импорт февраля тоже проходит и меняет annual; verify потом замечает часть ошибок, но запись уже произошла. Это неполный охват исходных зависимостей, а не требование доверять исправленному checksum.

**Исправить:** один валидатор пары CSV+manifest для КАЖДОГО месячного источника, с ожидаемым period из имени/реестра и cabinet/dataset/schema/bytes/count/hash/status; не доверять этим полям из самого manifest как ожидаемым. Проверять до использования. Включить соответствующие regression tests.

## R2 — известное повреждение годового файла проверяется после изменения месяца

Файл `archive.py:274–280`, `_publish:146–164`.

Воспроизведение: создать январь; испортить только annual CSV 10→99; импортировать исправленный январь со значением 20. Метод возвращает ValueError, но monthly CSV уже изменён. Сравнение снимков до/после подтверждает это. Добавленный автором test_b5_corrupt_ozon_annual_blocks_month_update проверяет исключение, но не отсутствие изменений месяца и backup-файлов.

**Исправить в рамках preflight:** под действующим lock проверить всю затрагиваемую группу (все используемые месяцы и текущий annual) ДО первой публикации/backup. На заранее повреждённом состоянии должен быть отказ без изменения бизнес-файлов. Это не заменяет многофайловую транзакцию B7: авария ПОСЛЕ чистого preflight по-прежнему требует recovery.

## B7 — совместимость и восстановление (отдельный незакрытый дефект)

Fault injection: OSError на `_safe_write` manifest после успешной записи CSV. Проверены первоначальная WB-публикация и обновление Ozon annual.

- Старая версия при повторе могла пересоздать manifest и завершала verify=True (но тем же механизмом допускала исходный B5).
- Новая версия корректно НЕ заверяет неизвестное/несогласованное состояние: повтор отклоняется, verify=False. Однако созданный самим publisher аварийный архив остаётся заблокированным до внешнего восстановления.
- Это безопасный fail-closed, а не основание удалить проверку. Но операционная совместимость без плана восстановления НЕ подтверждена. Нельзя лечить удалением manifest/пересчётом checksum/слепым повтором.

Нужны отдельные fault tests и процедура отката к проверенной паре/завершения подтверждённой generation. До реализации B7 явно документировать: ошибка импорта не гарантирует отсутствие изменений, повтор после прерванной публикации запрещён без проверки, применение к production не допускается. Версии исправлений B6 и ожидаемый inventory B8 этим PR также не закрыты.
