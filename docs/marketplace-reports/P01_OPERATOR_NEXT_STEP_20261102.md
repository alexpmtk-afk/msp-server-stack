## Что открыть и выполнить сейчас

1. На рабочем компьютере **WORK** откройте **WinSCP** и уже сохранённый/ранее использованный сеанс **старого Linux REMOTE**, из которого обслуживали Marketplace MCP и загружали историю. **Не сеанс нового VPS VM-817589.** Название вашего сохранённого сеанса мне неизвестно; не выдаю его за найденное.
2. Для выбора сеанса сверяйте адрес/порт/пользователя приватно с историческим Runtime path указанного source и вашей прежней записью подключения. У коллеги есть доступ к `gpt-powershell-bridge/main/.github/config/remote-endpoint.json`, но этот файл мог уже указывать на новый сервер: он не заменяет проверку старой записи/истории. Не пересылайте содержимое файла, IP, пароли или ключи.
3. Используйте только уже настроенное подключение с ранее проверенным ключом сервера. Если WinSCP показывает новый/изменившийся host key или сеанса нет — **остановитесь**, не соглашайтесь вслепую, не создавайте подключение/туннель и не запускайте bridge restore. Тогда достаточно сообщить «старый сохранённый сеанс отсутствует/доступ не работает».
4. В выбранном старом сеансе откройте **Команды → Открыть терминал**. Это Linux-терминал WinSCP, **не PowerShell нового VPS**. Вставьте целиком единственную физическую строку из [ONE_LINE_COMMAND.txt](operator/ONE_LINE_COMMAND.txt). Ничего сохранять на старом сервере не нужно. Читаемый исходник той же команды — [legacy_service_readonly.py](operator/legacy_service_readonly.py).
5. Пришлите только итоговый JSON. Команда не выводит hostname/IP/Redis URL/пароли/токены/Client-Id/значения окружения. Если Python отсутствует или доступа не хватает, не устанавливайте пакеты, не используйте sudo и не меняйте права; сообщите отказ без закрытых координат.

### Что даст эта команда

- Защита от ошибочного выполнения на известном новом VPS: STOP_WRONG_CONSOLE_NEW_VPS без systemctl scan.
- LoadState/ActiveState/SubState/User известной службы и факт активного PID.
- SHA git checkout у process cwd и SHA256 найденного core/archive_queue.py. Это on-disk/cwd свидетельства, не самостоятельное доказательство загруженного Python module origin; путь/версию необходимо затем сопоставить с launcher.
- При текущих достаточных правах — только признаки наличия selected Redis/storage полей в окружении процесса и boolean flags выбора backend. Значения не выводятся, credential files не читаются.
- Если служба не найдена/не запущена, команда не перебирает серверы и не запускает другой runtime. Ответ остаётся NOT VERIFIED, а не «старой инфраструктуры нет».

Команда **не** вызывает Redis, cloud API, WB/Ozon, application helpers, ensure_folder_path, job load/download, EVAL/admission, и ничего не записывает. Не добавляет расписания или фоновые процессы. Read-only диагностика уже разрешена владельцем; нового согласования на этот объём не требуется. Проверка команды: пять синтетических случаев PASS и shell quoting round-trip; **на старом сервере не выполнена**. [Протокол](operator/OFFLINE_VALIDATION.json).

После JSON я подготовлю следующий адресный READ_ONLY шаг именно для обнаруженного launcher/backend, а не общий scan: уточнение реального job-store class и приватное сопоставление Redis backend/DB/TLS/namespace. PING/TIME/INFO server и EXISTS/PTTL уже разрешены, но не должны выполняться на предполагаемом Redis или с guessed keys. Значения окружения и secrets на экран не печатать, AUTH URL в аргументы команд не вставлять.

## Минимальный план архива и реквизитов — только проект, НЕ выполнение

1. **Сначала placement и UID.** Подтвердить, что существующий worker имеет доступ к прежнему job-store и выбранному VPS. Если он на другом хосте, отдельно решить размещение/штатную доставку; не создавать новый scheduler и не переносить credentials на старый сервер автоматически.
2. **Private archive.** После отдельного admin approval создать только `/opt/mcp/data/msp-marketplace-reports`, закрепив владельца за утверждённым executor UID и права0700 (либо согласованную private read-group0750). Файлы0600; umask0077. Не менять владельца всего `/opt/mcp/data`, не давать777 и не использовать `/opt/mcp/secrets`. Проверку реальной записи/rename/fsync и временных файлов выполнить позднее в разрешённом deployment этапе.
3. **Реквизиты без chmod.** Сохранить исходные `/etc/msp-marketplace-reports` root0700 и cabinets.json root0600. Для непривилегированного существующего исполнителя рассмотреть **systemd LoadCredential** из root-controlled source в закрытый runtime credential directory выбранного unit/oneshot context, без нового постоянного демона/расписания. Модель описана в [официальной systemd.exec документации](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#LoadCredential=). Это копия секрета в защищённом runtime, поэтому требует отдельного утверждения; сейчас не создаётся. Сначала проверить версию systemd и metadata создаваемого файла/каталога: существующий load_credentials допускает файл с owner0 либо euid и закрытыми правами, отказывает symlink. JSON path передаётся явно; секрет не передаётся argv/env/log. Нельзя объявлять эту схему проверенной до настоящей установки и теста. Не запускать весь worker от root просто ради доступа к JSON.
4. **Минимальный допуск.** Выдать доступ только выбранному исполнителю и обоснованному набору кабинетов. Текущий cabinets.json содержит несколько кабинетов; если нужен отдельный минимальный credential-set пилота, его подготовка администратором — отдельное согласованное действие, не извлечение в чат/GitHub.
5. После утверждения placement/UID/credential mechanism подготовить точный diff установки/backup/rollback и согласовать изменяющий этап. Общая Redis admission/cooldown проверка и первый WB pilot имеют отдельные допуски. Сейчас всё перечисленное — **NOT INSTALLED / NOT EXECUTED**.
