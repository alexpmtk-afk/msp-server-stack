## Redis: что разрешено и почему не выполнено

Владелец уже разрешил узкие PING, TIME, INFO server и EXISTS/PTTL для точно определённых необходимых keys через существующий штатный доступ. **Повторного разрешения на эти же чтения не требуется.** Сейчас препятствие — отсутствие подтверждённого endpoint/config/host channel и ключей, а не недостаточная формулировка разрешения.

Не сделано ни одной Redis protocol command; список executed пуст. Не угадывался localhost/remote адрес; не использовались KEYS/SCAN/MONITOR/GET/SET/ZADD/EVAL/try_acquire/defer. Не выполнялся даже тестовый reservation/cooldown. Если существующий штатный оператор получит read-only результат на фактическом хосте в текущем разрешённом объёме, он устранит часть пробелов без создания новой инфраструктуры. Backend identity сопоставлять приватно, публиковать MATCH/MISMATCH/NOT_VERIFIED, не адреса/URL/DB credentials/owner keys.

PING/TIME/INFO и наличие keys сами по себе не докажут atomic admission, cooldown, fail-closed двух клиентов. Это следующий отдельно согласуемый изменяющий тест без HTTP, не часть текущего допуска. Отсутствие TTL/key в момент чтения также не равно неисправной квоте.
