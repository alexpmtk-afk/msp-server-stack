# B7 — предварительный контракт независимой аварийной приёмки

## Что есть сейчас и почему недостаточно

- `_safe_write` (строка 45): temp в том же каталоге, flush/fsync файла, replace и fsync каталога. Атомарность ОДНОГО имени не делает транзакцией несколько CSV/manifest.
- `_backup` (66): отдельные content-addressed копии CSV и manifest. Нет общего подтверждённого поколения/каталога транзакции и процедуры выбора пары. Существующий backup не перечитывается/проверяется перед использованием, потому что автоматическое recovery пока отсутствует.
- `_publish` (151): preflight → два backup → CSV → проверка SHA → manifest. Авария между публикациями оставляет разные версии пары.
- `_preflight_ozon_group` (278) защищает прежние месяцы/annual до записи; `_rebuild_ozon_annual` (302) вызывается после monthly. Корректный fail-closed после аварии может заблокировать следующий импорт, но это не восстановление.
- `_lock` (174) защищает cooperating writers одного cabinet/dataset. `verify` (341) не берёт тот же lock и не закрепляет поколение: при обычном импорте может увидеть промежуточную группу. Внешние читатели CSV также не имеют snapshot-контракта.
- `cli.py`: import/verify/status; recovery команды сейчас нет. B7 не должна превращать read-only verify/status в скрытую запись/восстановление.

## Обязательные инварианты перед реализацией

1. Определить transaction scope: WB CSV+manifest; Ozon CURRENT CSV+manifest; Ozon FINAL все затронутые monthly+annual CSV/manifest и привязанный каталог поколения. Другие кабинеты/годы/типы WB не откатываются.
2. Иметь один чёткий durable commit point. До него активен старый проверенный snapshot, после — новый целиком. Читатель не получает смесь; если выбран журнал вместо поколений, читатель удерживает общий lock либо отвергает незавершённое состояние. Указатель поколения без изменения всех читателей недостаточен.
3. Журнал/manifest поколения содержит transaction ID, expected parent generation, точный набор путей, SHA256/bytes/rows, identity/schema и состояния. Проверять его до применения; CSV и metadata недостаточно сопоставить по времени/похожему имени backup.
4. Не исправлять исходный повреждённый файл пересчётом SHA. Сохранять подозрительные файлы и доказательства; восстановление — только из независимо проверенного согласованного поколения. Повреждённый старый архив блокирует новую запись даже при исправном incoming CSV.
5. Для восстановления того же snapshot — та же строгая R3 типизация, identity/периоды/ключи, межмесячная/годовая согласованность. Provider coverage остаётся отдельной B8, восстановление не добавляет COMPLETE.
6. Recovery идемпотентно, также переживает собственную аварию и защищено тем же lock. Не откатывает более новое уже подтверждённое поколение из-за старого журнала.
7. Только локальный архив. Никакого Redis, API, запуска provider, чтения реквизитов и автоматического повторного скачивания при recovery. Ошибка/неопределённость не превращается в SUCCESS.

## Матрица обязательных испытаний

Все fixtures искусственные. Для каждого failpoint: snapshot всех файлов до и после; свежий процесс после отказа; verify active snapshot; проверка незатронутых групп; повтор recovery; повтор исходного импорта без потерь/дублей. Фиксировать имена файлов, SHA, generation/transaction IDs и статусы; не только exception.

## Как оценивать и что не выдавать за доказанное

- Monkeypatch OSError проверяет исключения, но `finally` ещё выполняется; SIGKILL нужен отдельно. SIGKILL не моделирует отключение питания/потерю fsync. Durability при power loss требует отдельного FS/VM crash-test или явного NOT VERIFIED; production VPS для этого не использовать.
- Для concurrent readers нужен согласованный интерфейс: простая последовательность `os.replace` нескольких файлов не даёт глобальной атомарности даже при качественном rollback. Только recovery после падения не решает чтение смешанного состояния во время обычной записи.
- Новая система не обязана внедрять конкретную технологию, но должна доказать перечисленные свойства. Не объявлять прежние раздельные `.bak` согласованным поколением задним числом.
- Число и место failpoints согласовать с фактическим будущим кодом; этот план — минимальные категории, не утверждение, что B7 уже реализована или испытана. Recovery API/политика запуска и совместимость читателей должны быть представлены разработчиком до приёмки.
