## 1. Как фиксируем КАЖДЫЙ результат

Обязательная последовательность: **действие → проверка → запись доказательства → инструкции/семантика → Skill → GitHub → read-back**. Само прохождение тестов не означает завершённый этап, пока нет общей записи и актуальных правил для исполнителей.

1. Записать ID задачи, дату/часовой пояс, исполнителя, точный commit, цель и предел полномочий. До работы перечитать текущие GitHub refs, HANDOFF, план и deployment manifest; назначить одного писателя на компонент.
2. После проверки отметить **PASS / FAIL / NOT VERIFIED** с уровнем: исходники, unit, изолированный Redis, CI, VPS, реальный API. Для неудачи также сохранить безопасное описание и следующий шаг.
3. В `HANDOFF.md` добавлять хронологию без переписывания истории. В `PROJECT.md` обновлять текущую рабочую карту, в `DECISIONS.md` — действующие решения и отмену устаревших правил. Разделять «предложено», «проверено», «слито», «установлено».
4. Версионировать семантику источников, документов и состояний, API/квоты, команды, ошибки и восстановление. Не менять существующую семантику баз МСП ради нового приложения. Никакие реальные токены, ответы с коммерческими/персональными данными, seller IDs или Redis passwords не публиковать.
5. Сначала обновлять канонический Skill проекта в репозитории (планируемый путь `apps/hermes/msp_marketplace_reports_skill/`): SKILL.md — вход и маршрутизация, references — квоты, источники, полнота, recovery, эксплуатация. До появления такого Skill процедуру аудита хранит существующий data-pipeline-operations. Непроверенное не записывать как рабочую команду.
6. Обновлять установленный Skill Hermes только проверенными применимыми инструкциями; фиксировать источник/SHA/хеши и статус установки. Изменение инструкций не означает установку кода или разрешение API. Навыки, installer и серверные docs должны быть согласованы; не ограничиваться личной памятью одного чата. Другие профили без поручения не менять.
7. Публиковать небольшой commit/PR, читать обратно SHA/точный файл и CI. Слияние и production-установка — отдельные разрешения. До слияния в рабочей карте и HANDOFF явно указывать, какой открытый PR содержит последнюю версию.
8. После разрешённой установки записывать deployment manifest: точный принятый commit, файлы/хеши, backup, применённые миграции, тесты, состояние допуска, порядок отката. Коллеги должны видеть разницу GitHub и VPS.

Предлагаемые проектные документы, создаваемые по мере соответствующих этапов: `SOURCE_CONTRACTS.md`, `RATE_LIMIT_CONTRACT.md`, `ARCHIVE_SEMANTICS.md`, `OPERATIONS.md`, `ACCEPTANCE.md`. Сейчас это названия будущих артефактов, не уже существующие источники правил.

### P03. Исправить квоты и сетевой транспорт — B1, B2

Файлы: `quota.py`, `shared_rate_limit.py`, `runtime.py`.

- Совместить точный WB bucket `finance` со старым контрактом, сохранив защитный интервал дополнительным ограничением. Проверять endpoint, DB, seller hash и итоговые ключи, а не только наличие Redis.

- Команды «что отсутствует», «дозагрузить», «перепроверить» разделить по полномочиям; API-действия только с подтверждённым допуском. Логи/наблюдение должны показывать очередь, прогресс, ошибки и ресурсные пределы без секретов.
- Выполнить приёмку через реальный разрешённый вход Hermes и интерфейс другого клиента; инструкции из GitHub должны воспроизводимо давать тот же статус архива. Не обещать автоматическую общую историю разных чатов.
- Обновление по запросу — базовый режим. Расписание, часовой пояс, окно корректировок и ресурсные пределы обсуждать отдельно; до отдельного решения таймеров нет.
- **Готово:** OPERATIONS/ACCEPTANCE, канонический и установленный Skill, deployment manifest и registry согласованы; восстановление и read-only интерфейс проверены; владелец принимает результат с явно указанными ограничениями.

## 3. Зависимости и начало

P01 + P02 → P03; P04–P06 разрабатываются в изолированных ветках с учётом контрактов → P07 → отдельные согласования P08 → узкие допуски P09/P10 → отдельный допуск P11 → итоговая приёмка P12. Документация/Skill — обязательная часть каждого шага, не задача «на потом».

**Ближайшее действие — P01: карта фактической общей очереди и разрешённого доступа.** P02 и офлайн-подготовка исправлений не требуют обращения к кабинетам. Если нет read-only доступа к старому runtime, подготовить минимальную проверяемую диагностику для владельца; не выдумывать результат и не просить токены/пароли в чате.

План не предполагает автоматического выполнения всех защищённых этапов после одной общей фразы «приступаем»: прежние явные запреты и отдельные точки допуска сохраняются.
