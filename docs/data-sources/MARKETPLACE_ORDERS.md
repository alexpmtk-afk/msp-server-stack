## Как должны работать все потребители

1. При запросе «сколько заказов по дням», «динамика заказов за недели/месяцы», «заказы за прошлые месяцы», «заказы по карточке» начинать с этой карты. Проверить регистрацию источника и право текущего инструмента его читать. **Само наличие GitHub-ссылки НЕ даёт доступа к Google Sheets/QRsite/внутреннему сайту.**
2. Для однозначного продукта использовать ключ `marketplace + store + marketplace_sku`, а при необходимости связать с внутренним артикулом через `product_listing`. Сохранить отдельные показатели каждого кабинета и площадки.
3. **Заказы** = созданные заказы, **продажи/выкупы** = оплаченные или завершённые по семантике источника; не использовать одно вместо другого. Отдельно производственные заказы `production_metal_order`/`production_sewing_order` — это выпуск продукции, не спрос покупателей.
4. Не смешивать месячную, недельную и дневную агрегацию и **не складывать перекрывающиеся временные окна**. Метрики `orders_count`, `orders_sum`, отмены, часовой пояс, дата среза и полнота ряда должны проверяться **по конкретным колонкам реального отчёта** перед публикацией схемы.
5. Для текущего дня / недели проверять время последнего обновления источника. Отсутствие доступа или данных = `SOURCE_UNAVAILABLE` либо `NOT_VERIFIED`, а не ноль заказов.
6. Для SIG-002 «Поднять цену» использовать **готовое `_N` из Telegram**, не пересчитывать его по этому отчёту. Отчёт заказов полезен для отдельных задач аналитики спроса, но это другой сценарий.
7. Обязательное доказательство внедрения — два независимых теста: Hermes показывает источник и реально получает проверяемый период; второй независимый чат/приложение с доступом к нужным знаниям находит эту карту и получает тот же период. PR, Skill и копия файла в Git сами по себе **не доказывают** работающую общедоступность.
